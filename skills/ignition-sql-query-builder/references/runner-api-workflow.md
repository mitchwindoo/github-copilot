# Runner API Workflow

## Source And API Routes

- For Tag Historian/PostgreSQL partition work, read `references/historian-postgres-guardrails.md` before writing SQL.
- For runner API work, start with `health`; confirm `runnerVersion`, `supportedActions`, `readOnlyNamedQueryActions`, and named-query feature flags before relying on SQL previews. Treat `supportedActions` as the callable action catalog; `readOnlyNamedQueryActions` is a convenience list for `namedQueriesList`, `namedQueryRead`, and `namedQueryPreview`, not a replacement for action discovery.
- Use `gatewayInfo` only for target context. A live Gateway stack can lag behind the source/package stack; do not refresh or self-update the runner unless the user explicitly asks or the task explicitly includes runner API improvement.
- On runner `0.3.63+`, use `databaseConnectionsList` before driver-specific SQL, Tag Historian/PostgreSQL work, or Database-parameter diagnostics. Inspect database type, status, and count. If the target has only SQLite, no valid PostgreSQL connection, or no relevant non-SQLite connection, say that the driver-specific behavior is target-dependent and unproven instead of extrapolating from another target. Treat returned connection names and problem text as target-local evidence; use placeholders such as `<databaseConnection>` in reusable SQL and docs.
- Use `namedQueriesList` to discover existing query paths, query types, params, SQL hashes, `readOnlyEligible`, and `boundedPreviewEligible`.
- Use `namedQueryRead` before previewing or building a page. Treat returned SQL and metadata as the source of truth; do not invent table names, params, database names, or columns.
- On runner `0.3.64+`, the Named Query preview/package SQL scanner is quote/comment-aware and package validation checks packaged `Query`/`ScalarQuery` dependency SQL for read-only preview eligibility. CTE/`WITH` queries, SQL-looking text inside balanced comments, SQL-looking text inside string literals, and a single trailing statement semicolon are accepted by the tested runner path; semicolon-chained dependency SQL is rejected during package `dryRun`/`apply` before execution. Do not rely on block comments for row bounds or statement separation: malformed or nested block comments can pass structural read-only checks yet fail bounded preview or database parsing. Still generate one clear bounded statement and avoid a trailing semicolon unless the target style requires it.
- On runner `0.3.62+`, pass `includeResourceJson: true` when copying an existing Named Query into a package. Package the returned raw `resource.json` exactly with `query.sql`; do not reconstruct Named Query `resource.json` from summary metadata or hand-author parameter `sqlType` metadata from memory. A reconstructed resource can pass package/page/read checks while failing runtime `system.db.runNamedQuery`, especially when scope/version, cache/fallback fields, permissions, and Ignition parameter metadata do not match the target export shape. A file-level `namedQueryRead` can still see a resource that the project runtime does not load correctly; after apply, prove execution with `namedQueryPreview` or a deliberate `system.db.runNamedQuery` check before using the copied query.
- Use `namedQueryPreview` only after `namedQueryRead` shows an enabled read-only bounded query. Keep `maxRows` inside the runner cap; on runner `0.3.96+`, the DB-side `LIMIT`/`TOP`/`FETCH` or Named Query max return size must be no larger than request `maxRows`, not merely no larger than the global preview cap. On runner `0.3.99+`, only top-level outer-query numeric `LIMIT`/`TOP`/`FETCH` row limiters count as SQL proof; nested-only subquery/CTE limiters, `TOP PERCENT`, `TOP/FETCH WITH TIES`, dynamic limits, and nonliteral limits reject unless a safe Named Query max return size is enabled. Use returned `columns`/row objects to design Perspective tables.
- For `ScalarQuery` Named Queries on runner `0.3.63+`, require `namedQueryRead` to show `queryType: "ScalarQuery"`, `readOnlyEligible: true`, and `boundedPreviewEligible: true` before previewing. A successful `namedQueryPreview` summarizes the return as a scalar-shaped result, typically one `value` column/field rather than the original SQL column aliases. If the scalar SQL returns SQL `NULL` or no rows, preview can still report a scalar `value` shape while returning no usable value; do not use scalar preview as rowset schema proof or as proof that `NULL` and no row are distinguishable. Use scalar previews for counters/status values, not table-column design.
- Keep preview SQL explicitly DB-side bounded even for finite sample `UNION ALL` rowsets. A human-obvious finite select list can still be rejected as unbounded by preview safety classification unless it has an explicit `LIMIT`, `TOP`, `FETCH`, or approved max-return bound within the runner cap.
- For `namedQueryPreview`, pass raw parameter values such as `{"matchText": "<matchPattern>"}`. This proves server-side Named Query execution, not Perspective client parameter expression syntax.
- For package `dryRun`/`apply`, treat `dependencyNamedQueryPaths` as a packaged-resource contract: every listed path must exist inside the zip under `ignition/named-query/<path>/resource.json` and `query.sql`. Do not use it as a target-only existence list.
- If a packaged dependency Named Query contains `QueryString` or `Database` params, expect package `dryRun`/`apply` to reject it by default. Only use the diagnostic override for copied read-only, allowlisted cases: set `allowUnsafeNamedQueryParameters: true`, include the path in both `dependencyNamedQueryPaths` and `unsafeNamedQueryParameterPaths`, and set `confirmUnsafeNamedQueryParameters: "ALLOW_UNSAFE_NAMED_QUERY_PARAMETERS"`; still preview `QueryString` values with `allowQueryStringParameters: true` plus a narrow `queryStringParameterAllowlist`, and verify non-allowlisted SQL-looking values fail before execution.
- After applying a package-managed Named Query page, verify all three layers: `pageValidate` with the same `dependencyNamedQueryPaths`, `viewRead` for the table binding path/fields, and `namedQueryRead` plus `namedQueryPreview` on the copied query path. `pageValidate` proves route/view/resource structure only; it does not prove runtime query execution or browser rendering.
- When the deliverable is a visible Perspective page, add browser/client proof after API checks pass. Open `<gatewayUrl>/data/perspective/client/<projectName>/<pagePath-without-leading-slash>`, confirm the expected title or label, copied query path when shown, preview-derived table headers/rows for non-empty results, and no relevant client console errors for query bindings/components before claiming render success. For zero-row previews, do not rely on an empty IA Table to expose column headers; add and check a separate visible status/column label from preview metadata, such as `Preview columns: displaypath, eventtime`, plus query-bound row-count or empty-state text. Do not accept a zero-like label, blank table, fallback/default text, or absence of console errors as proof of a valid empty result by itself; confirm that `namedQueryPreview` succeeds with the same required parameter map and that `viewRead`/view JSON passes every required parameter. A missing required Perspective query-binding parameter can leave fallback/default UI visible with no relevant browser console errors. For paged IA Tables, do not assume every row in the current page is present in the browser DOM: the default pager may be 25 rows while the rendered DOM is virtualized to the visible viewport. Prove paging with a query-bound row-count/status label, a visible first-page row, absence of an off-page row before paging, a unique pager control such as exact visible page number text, and the off-page row after clicking the next page/control.
- For query-binding polling or refresh claims, treat `namedQueryPreview` as a single server execution only. Set `config.polling.enabled` and `config.polling.rate` intentionally, add a visible query-bound status label such as a timestamp/tick plus a row-count label, and browser-test that the visible value changes without user input or page reload. A static render or a successful preview does not prove ongoing polling.
- For manual query-binding refresh claims, API preview, `pageValidate`, `viewRead`, and event-script compile checks are not enough. Put the query binding on a specific component/property, call `refreshBinding("<boundPropPath>")` on that exact component, and browser-test that the visible query value stays stable before the user action and changes after it. For example, if a Label owns a query binding on `props.text`, a sibling Button can call `self.getSibling("<LabelName>").refreshBinding("props.text")`. If an IA Table owns the query binding on `props.data`, refresh the Table's `props.data` with `self.getSibling("<TableName>").refreshBinding("props.data")`; do not refresh the parent container, table columns, or an unrelated status label. For table refresh proof, derive a visible row-count/tick/status label from the Table's `props.data` or verify actual changing row values, because table cell rendering, paging, and virtualization can make DOM-only checks ambiguous. Disable polling when proving manual-only refresh, and add a visible click/status echo so a failed refresh cannot masquerade as an unclicked button.
- Treat JSON error envelopes from preview rejection as useful safety evidence. Missing params, unexpected params, over-cap previews, unbounded SQL, nested-only SQL row bounds, update/query-action types, prefix escapes, QueryString params, and Database params should fail before execution unless an exact diagnostic allowlist is supplied. On runner `0.3.98+`, Named Query prefix escape means exact-or-child matching, so `Reports/A` must reject siblings such as `Reports/ABC`. Use those preview errors to catch parameter-map issues that runtime may otherwise coerce to `NULL` or ignore.
