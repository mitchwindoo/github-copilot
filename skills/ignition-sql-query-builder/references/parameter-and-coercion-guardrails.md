# Parameter and Coercion Guardrails

## Parameters

- Require every declared Named Query parameter before preview/run. Also require every declared parameter in Perspective query bindings; do not omit a required binding parameter to mean empty, all rows, or default behavior. Map those states to an explicit sentinel or nullable value that is still passed under the declared parameter name, then branch intentionally in SQL. Treat runner preview rejection as the stricter safety gate: preview rejects missing, unexpected, and list-shaped parameter maps before execution. Runtime `runNamedQuery` on the tested Query-type Value-param target treated a missing declared param as SQL `NULL` and ignored an extra map key, so never treat a quiet runtime row as proof the parameter map is correct.
- Reject unexpected parameter names before runtime to catch typos, and pass exactly one params dictionary/Map. Use explicit `None` or an allowlisted sentinel for intentional null/default/all behavior instead of relying on omitted-key behavior from one target.
- Treat Named Query `Value` parameter coercion as target-specific. Parameter metadata does not guarantee that JSON, Perspective, or Jython numbers, booleans, and timestamps bind as database-native numeric/boolean/timestamp values. UI, URL, and Perspective values often arrive as strings; validate and normalize before passing where practical, or cast/parse deliberately in SQL with explicit companion fields such as `value_parse_state`, `value_is_null`, `row_count`, or `invalid_reason` when invalid, zero, false, empty, and null states matter. Verify native JSON numbers, numeric strings, false/zero, invalid text, and explicit nulls on the target database. Do not assume invalid numeric/date text fails automatically: some targets or functions can coerce invalid numeric text to zero or invalid date text to `NULL`.
- Treat API preview parameter maps and Perspective query-binding parameter maps differently. API calls pass raw values; Perspective binding `config.parameters` entries are expression/property-reference strings. For a literal string constant, JSON-encode an Ignition expression string literal such as `"\"<matchPattern>\""`. Passing a raw wildcard string directly in a Perspective binding can be parsed as an expression using `%`/MOD and render a component error. For dynamic values, use property references such as `"{view.params.asset}"`, `"{view.params.matchText}"`, `"{../Input.props.text}"`, or `"{../FilterDropdown.props.value}"`. When a browser-edited `ia.input.text-field` drives a query parameter through a sibling reference such as `"{../FilterInput.props.text}"`, inspect or set `props.deferUpdates` intentionally. With `deferUpdates: true`, typed text can be visible in the browser input while bound `props.text` consumers and query-backed labels/tables still use the previous committed value until Enter or blur. With `deferUpdates: false`, the immediate-update TextField pattern should refresh the bound echo/table from the typed value without Enter or blur. For enum/select filters, use explicit Dropdown option `value` entries that are valid SQL parameter values, bind the Named Query param from `props.value`, and browser-test at least one matching option plus one no-match or alternate option. If Dropdown options come from a query binding, return stable `label` and `value` columns from the options Named Query or add a script transform that converts Dataset/PyDataSet or row-list results into option objects like `{"label": str(label), "value": str(option_value)}`; keep the selected `props.value` scalar and use that scalar for downstream Named Query params. For multi-select Dropdowns, set `props.multiSelect: true` and treat `props.value` as an ordered list of selected option values. Do not pass that list into one SQL/Named Query parameter as a pretend dynamic `IN` list; for a bounded small multi-select filter, declare scalar parameters per slot and bind them with indexed property references such as `"{../FilterDropdown.props.value[0]}"` and `"{../FilterDropdown.props.value[1]}"`. Branch empty, missing, or null slots intentionally in SQL, or require a fixed number of selections before running the query. Browser-test both selected-pill removal and clear-all when enabled with `props.showClearIcon: true`: removing one pill shifts selected-value indexes, while clear-all can leave every indexed slot null/missing. For optional "all rows" select filters, prefer an explicit allowlisted sentinel value such as `__ALL__` over omitting the parameter; keep the Named Query parameter required, branch in SQL with a bounded predicate such as `:matchText = '__ALL__' OR displaypath LIKE :matchText`, and API/browser-test match, no-match, and all-state values. If the UI needs a user clear button, use the documented Dropdown `props.showClearIcon: true` property rather than an invented `clearable` prop, and define `props.placeholder` as an object such as `{"text": "Choose a filter"}`. Treat a cleared single-select Dropdown as a nullable value unless the design maps clear to an explicit sentinel; keep the required Named Query parameter present and branch SQL intentionally, for example `:matchText IS NULL OR :matchText = '' OR displaypath LIKE :matchText`, then API/browser-test match, no-match, and clear/null states. For any input mode, browser-test the chosen update behavior instead of assuming it from the component default.
- For Checkbox filters, bind boolean state from `"{../FilterCheckbox.props.selected}"`, add a visible selected-state echo plus a query-derived row-count/status label, and browser-test checked, unchecked, and rechecked states. Treat the bound value as target-coerced data, not guaranteed database-native boolean: normalize or branch deliberately for native true/false, string `true`/`false`, numeric-looking `1`/`0`, explicit null, missing params, unexpected params, and invalid text when the SQL distinguishes those states.
- For Numeric Entry Field filters, bind numeric input from `"{../MinValue.props.value}"` or the actual sibling component name, add a visible numeric-value echo plus a query-derived row-count/status label, and browser-test the initial value plus at least two edited values such as a decimal threshold and zero/all-state threshold. The official Perspective Numeric Entry Field docs define `props.value` as a number or numeric string and support `direct`, `protected`, and `button` edit modes, so choose the edit mode intentionally and prove it in the browser. Treat the bound value as target-coerced data, not guaranteed database-native numeric: normalize or branch deliberately for native numbers, numeric strings, decimals, zero, explicit null/empty, missing params, unexpected params, and invalid text when the SQL distinguishes those states. On tested Named Query preview/browser paths, numeric values can still arrive at SQL as text, so add parse/status/display companions such as `param_state`, `param_text`, `threshold_value`, `threshold_display`, and `row_count` when the UI must distinguish invalid, null/default, zero, and filtered states.
- For Radio Group filters, define explicit `props.radios[].value` entries, bind the downstream query parameter from the component's `props.value`, add a visible selected-value echo plus a query-derived row-count/status label, and browser-test the initial value, at least two option changes, and any all-state/default option. The official Perspective Radio Group docs define `props.value` as the selected radio value and allow string, integer, boolean, or null values; treat that value as target-coerced data and branch deliberately for allowlisted values, case/normalization choices, explicit all-state sentinels such as `__ALL__`, null/empty/default, invalid, missing-param, and unexpected-param states when they matter.
- For DateTime Input filters, bind the downstream query parameter from the component's `props.value`, add a visible DateTime value echo plus a query-derived row-count/status label, and browser-test initial/in-range, alternate in-range, future/no-row, and clear/null states. The official Perspective DateTime Input docs define `props.value` as a Date object or timestamp in milliseconds and expose display/input properties such as `formattedValue`, `pickerType`, `minDate`, `maxDate`, `format`, `locale`, and `dismissOnSelect`; treat the bound value as target-coerced data, not guaranteed database-native timestamp. Normalize or branch deliberately for epoch-millis, ISO/date text, explicit null, empty/default, future/no-row, invalid text, missing-param, and unexpected-param states when they matter. Preserve target-exported Named Query resource metadata when adapting existing date queries, and prove DateTime/Timestamp parameter metadata on the target before relying on it.
- Treat a syntactically present Perspective property-reference string as structure, not runtime proof. `pageValidate` and `viewRead` can preserve `config.parameters` entries such as `"{../Input.props.text}"` even when the referenced component or property is missing; at runtime that can feed SQL `NULL`, hit a default/all-rows branch, or surface as a binding error. For any nullable/default/all branch that could hide a typo, add visible value/state/row-count echoes and browser-test both the intended reference and at least one missing-reference negative control before claiming the binding is correct.
- For TextField/search filters that feed SQL `LIKE`, decide whether typed `%` and `_` are intended wildcards or literal characters before binding. Named Query `Value` params prevent SQL injection, but they do not make `LIKE` metacharacters literal. Leave a raw TextField value such as `:matchText` only for deliberate wildcard mode. For literal search, build an escaped companion value in trusted code before binding, for example `!` -> `!!`, `%` -> `!%`, and `_` -> `!_`, then use SQL such as `displaypath LIKE :escapedText ESCAPE '!'`; adding `ESCAPE '!'` alone does not stop unescaped `%` or `_` from acting as wildcards. API-preview and browser-test both a wildcard case and a literal escaped case, with a visible input echo, row count, and row list/table so wildcard-confuser rows cannot hide.
- For Text Area filters, bind multiline text from the component's `props.text`, for example `"{../FilterTextArea.props.text}"`, not from a guessed `props.value`. The official Perspective Text Area docs describe it as multiline text display/editing and define `text` as a string, `deferUpdates` as deferring `props.text` updates until focus is lost or Enter is pressed, and `wrap` as the line-wrapping control. Add a visible text echo that normalizes line breaks for display, such as replacing newline with `<LF>`, plus a query-derived row-count/status label. If `props.deferUpdates` is true, browser-test a focused uncommitted edit separately from the committed blur/Enter state; for multiline entry, prefer a real keyboard edit plus Tab/blur commit proof because synthetic DOM fills can miss the component's commit path. Use API preview to prove multiline text, single-line text, empty/default, null/default, no-match or partial text, SQL-looking text, missing-param rejection, and unexpected-param rejection when those states matter. Treat newline content as data passed through a Named Query `Value` parameter; do not concatenate it into SQL or switch to a QueryString parameter for user-entered text.
- Use raw Jython `system.db.runQuery` only for trusted fixed `SELECT` text with no user, URL, Perspective property, tag, or variable values. It is a standard-statement helper, not a prepared-parameter helper: do not use `?` placeholders or pass parameter lists/dictionaries to `runQuery`. Use Named Query `Value` params or `system.db.runPrepQuery` when values must be supplied dynamically. `runQuery(sql, <databaseConnection>[, tx])` returns a PyDataSet rowset; check row/column counts before indexing and expect empty results to preserve column metadata. In reusable Gateway/Perspective helpers, pass the database connection explicitly unless a default database dependency is intentional and target-verified.
- Use raw Jython `system.db.runUpdateQuery` only for trusted fixed `INSERT`/`UPDATE`/`DELETE` text with no user, URL, Perspective property, tag, or variable values. It is a standard-statement write helper, not a prepared-parameter helper: do not use `?` placeholders or pass parameter lists/dictionaries to `runUpdateQuery`. Prefer Named Query `Value` params or `system.db.runPrepUpdate` when values must be supplied dynamically. By default, `runUpdateQuery(sql, <databaseConnection>[, tx])` returns affected-row count; expect `1` for a single-row insert/update/delete, `0` for a legitimate no-match update/delete, and flag unexpected counts. Use `getKey=1` only when the target database, driver, table definition, and statement support generated-key retrieval, then verify the returned key with follow-up readback. Keep `skipAudit=True` explicit and rare. For write probes or migrations, pass the database explicitly, keep `tx` separate, rollback during tests, and verify post-rollback or cleanup state because DDL lifecycle and generated-key behavior are driver-specific.
- Treat `UpdateQuery` Named Queries as writes/action calls, not previews. `namedQueryPreview` should reject them before execution; use `namedQueryRead` for metadata and execute only through intentional script code. Call `system.db.runNamedQuery(<projectName>, <namedQueryPath>, params)` for the write, check the returned affected-row count, and verify durable readback or rollback state on the target. Use keyword `getKey=1` only when generated keys matter and the target database/table/query support it, then verify the returned key with a follow-up read. Keep params as one dictionary/Map, not a list, and pass every declared param explicitly; if a nullable omitted param appears to work on one target, still prefer an explicit `None` or sentinel value and verify behavior.
- Treat `ScalarQuery` Named Queries as scalar contracts, not rowset contracts. `system.db.runNamedQuery(<projectName>, <namedQueryPath>, params)` returns the first column of the first row as a plain scalar for `ScalarQuery`; later columns and later rows are outside the contract. Both a first-column SQL `NULL` and zero returned rows can surface as a `None`-like result, so use a Query-type rowset with explicit companion columns such as `row_count`, `value_is_null`, or a sentinel value when the UI or script must distinguish empty from null. Pass one params dictionary/Map, not a list. If a declared value may be empty or optional, pass an explicit `None` or sentinel and branch intentionally instead of relying on omitted-parameter behavior from one target.
- In script transforms or Project Library helpers that consume Query-type Named Query results or prepared-query reads, treat results as Dataset/PyDataSet-like values. Use `getRowCount()`/`getColumnCount()` before row access and `getValueAt(row, columnIndex)` for direct single-value reads; use name-based access only when the returned object supports it. Normalize with `system.dataset.toPyDataSet(value)` before iterating rows or using `row["<columnName>"]`, then convert rows to plain dictionaries or option objects before returning data for Perspective table/options helpers. Empty results can still preserve column metadata while `len(system.dataset.toPyDataSet(value))` is `0`, so never index row 0 until the row count is positive. Do not use truthiness to decide whether a query value exists: `None`, `""`, `0`, `0.0`, and false-like numeric zero can all be falsey in Jython while meaning different SQL/UI states. Use explicit `value is None`, string length checks, numeric comparisons, and row-count guards.
- Use `system.db.runScalarQuery` or `system.db.runScalarPrepQuery` only when the intended contract is exactly one first-row/first-column value, such as `COUNT(*)`, `MAX(...)`, or a status value. Scalar calls return a plain scalar, not a Dataset/PyDataSet; later columns and later rows are discarded. Treat `None` carefully: it can represent a SQL `NULL` in the first row/column or no returned rows at all. If the difference between zero rows and SQL NULL matters, use a rowset query with row-count checks or return explicit companion columns such as `row_count` and `value_is_null`. `runScalarPrepQuery` still uses the same ordered list/tuple parameter rules as other prepared calls.
- For route-parameter query pages, declare the route input as a plain top-level view param such as `"params": {"matchText": ""}` with `propConfig["params.matchText"].paramDirection = "input"`, bind the Named Query param to `"{view.params.matchText}"`, validate the dynamic route key such as `/query/:matchText` with `pageValidate`, and browser-open concrete match and no-match URLs. Keep path segment values route-safe: asset IDs, slugs, or exact text filters are safer than SQL wildcard strings. Do not borrow query-string `+` decoding assumptions for path segments: in dynamic route behavior, `%20` decoded to a space and returned matching rows, while raw `+` and `%2B` both rendered as a literal plus value and returned no matching rows. Encode spaces as `%20` and literal plus signs as `%2B` when generating path URLs. Treat raw `?` as a path/query-string delimiter, not a value character: in dynamic route behavior, encoded `Asset%3FHigh%3DAlarm` rendered `view.params.matchText` as `Asset?High=Alarm` and left `page.props.urlParams.High` null, while raw `Asset?High=Alarm` rendered `view.params.matchText` as `Asset` and `page.props.urlParams.High` as `Alarm`. Encode literal question marks as `%3F` and literal equals signs as `%3D` inside path segment values, and browser-check the visible `view.params.<name>` echo, any split-prone `page.props.urlParams.<name>` echo, and the row-count/table result. Treat raw `#` as a browser fragment delimiter inside path segments: in dynamic route behavior, encoded `Asset%23High%3DAlarm` rendered `view.params.matchText` as `Asset#High=Alarm` and left `window.location.hash` empty, while raw `Asset#High=Alarm` rendered `view.params.matchText` as `Asset` and left `window.location.hash` as `#High=Alarm`. Encode literal hash signs as `%23`, and browser-check the visible route-param echo, row-count/table result, and `window.location.hash` when hashes may appear. Treat raw `/` as a path separator; encode a literal slash as `%2F` only when it must remain inside one route parameter segment. In dynamic route behavior, `Asset%2FHigh%2FAlarm` rendered `view.params.matchText` as `Asset/High/Alarm` and left `page.props.urlParams.High` null, while raw `Asset/High/Alarm` created extra path segments and missed the configured route with a View Not Found/no-view state. Browser-test slash-containing values through the client path because route handling or reverse proxies can normalize encoded slashes differently. Do not depend on an encoded `%` wildcard such as `%25` inside a Perspective path segment; it can fail route decoding before the query binding runs. For wildcard search, prefer a TextField/form input or another target-verified transformation outside the URL path segment.
- For Button or script-driven dynamic-route navigation, pass the Perspective page path by keyword with `system.perspective.navigate(page=<page path with a concrete route-safe segment>)` when the target is another route path in the same project. This is distinct from query-string navigation: `page` is for Perspective page paths, while `url` is for full web/client URLs with query strings. Browser-test the click by checking the URL path, visible `view.params.<name>` echo, row-count/table state, expected row presence or absence, and relevant console errors.
- For Button or script-driven in-page view navigation with parameters, use `system.perspective.navigate(view=<view path>, params={<name>: <value>})`. The `params` dictionary is for `view` navigation, not `page` or `url` navigation. Declare matching input view params, bind the Named Query from `"{view.params.<name>}"`, and browser-test that the URL stays on the mounted page while the visible view-param echo, row count, table state, expected row presence/absence, and relevant console errors change as intended.
- Do not assume a URL query string on a static Perspective page route populates top-level `view.params` or automatically drives a Named Query binding. A browser-opened page such as `/query-page?matchText=<encodedNoMatchValue>` can have that value in `window.location.search` while `"{view.params.matchText}"` and the table binding still use the view param default. For query-string-driven filters, use the read-only Perspective page property `page.props.urlParams`, add a visible echo, and browser-test match/no-match URLs. A direct static-route pattern binds the Named Query parameter from `"{page.props.urlParams.matchText}"`; match and no-match query-string URLs changed the visible URL-param echo, row count, and table together. Test omitted and empty query-string values separately when a URL filter has an all/default state: when binding directly from `page.props.urlParams`, omitting `?matchText` resolved the URL-param binding as `null`, while `?matchText=` resolved as an empty string. Keep the Named Query parameter present and branch intentionally, for example `:matchText IS NULL OR :matchText = '' OR displaypath LIKE :matchText`, or normalize both states through a bridge/sentinel before the query. Do not use repeated same-name query-string keys such as `?matchText=A&matchText=B` as a multi-select or dynamic `IN` shortcut; with a direct `page.props.urlParams.matchText` binding, the property and dependent Named Query parameter resolved to the last repeated value. Do not use bracket-style query-string keys such as `?matchText[0]=A` or `?matchText[]=A` as array shortcuts either; Perspective surfaced those as literal `page.props.urlParams` keys (`matchText[0]`, `matchText[]`) and did not populate `page.props.urlParams.matchText`. If both plain and bracketed forms are present, the plain scalar binding is what the Named Query receives. For multi-value URL filters, use distinct allowlisted parameter names/slots or a target-verified bridge/normalizer that exposes exactly what SQL params will receive. Encode query-string values deliberately: prefer `%20` for spaces when generating URLs, because both `%20` and `+` decoded to a space in direct bindings, while `%2B` decoded to a literal plus sign. If a literal `+` is part of the intended SQL value, encode it as `%2B` and browser-test the visible decoded echo plus row-count/table result. Encode literal query-string delimiters too: use `%26` for `&`, `%3D` for `=`, `%23` for `#`, and `%25` for `%` when those characters are part of the URL value. URL encoding does not escape SQL `LIKE`: in direct bindings, `matchText=Asset%25High%25Alarm` decoded to `Asset%High%Alarm`, and the decoded `%` characters still acted as SQL wildcards when passed to `displaypath LIKE :matchText`, returning matching rows. If the intended URL value contains the literal characters `%25`, encode the percent again as `%2525`; if the intended SQL comparison is a literal percent sign, use equality or explicit `LIKE` escaping with an `ESCAPE` clause/normalizer instead of relying on URL encoding. An unencoded `&` starts a separate query parameter in direct bindings, so `?matchText=Asset&High=Alarm` delivered `matchText` as `Asset` and `High` as `Alarm`, while `?matchText=Asset%26High%3DAlarm` delivered `matchText` as `Asset&High=Alarm` and no `High` param. A raw `#` starts the browser URL fragment before the value reaches `page.props.urlParams`: in direct bindings, `?matchText=Asset%23High%3DAlarm` delivered `matchText` as `Asset#High=Alarm` with an empty `window.location.hash`, while `?matchText=Asset#High=Alarm` delivered `matchText` as `Asset` and left `window.location.hash` as `#High=Alarm`. For delimiter-sensitive URL filters, add visible echoes for every parameter that could split and browser-test the decoded values, dependent SQL result, and fragment state when `#` might appear; for `LIKE` filters, also browser-test the row count/table result for decoded `%` values. A bridge pattern also works: bind `page.props.urlParams.matchText` into `view.custom.matchText`, then bind the Named Query parameter from `"{view.custom.matchText}"`. Use the bridge when you need an intermediate property for normalization, defaulting, reuse, or clearer debugging. Otherwise use route-safe dynamic path segments for exact values or visible input components for wildcard search.
- In SQL `LIKE`, both `%` and `_` are wildcards. URL encoding only transports those characters; it does not make either one literal after the value is decoded and bound as a Named Query `Value` parameter. When the SQL comparison must treat `%` or `_` literally, prefer equality or a target-verified normalizer/escape function. If using `LIKE ... ESCAPE '!'`, pre-escape the parameter value itself, for example `!` -> `!!`, `%` -> `!%`, and `_` -> `!_`; adding an `ESCAPE` clause alone does not stop an unescaped `%` or `_` from acting as a wildcard. API/browser-test both wildcard and literal-match cases.
- Do not assume `LIKE` or `=` case behavior is portable. Case sensitivity depends on the database, collation, connection/session settings, and operator (`LIKE`, `=`, `ILIKE`, `COLLATE`, etc.). When case matters, API-preview and browser-test exact, lower, and upper case values on the target. For required case-insensitive matching, use a target-verified normalizer or collation such as `LOWER(column) = LOWER(:param)`, `ILIKE`, or `COLLATE`, and check index/performance effects.
- For bounded multi-value URL filters, declare one required Named Query `Value` parameter per scalar slot, such as `match0` and `match1`. Bind each slot from a distinct property such as `"{page.props.urlParams.match0}"` and `"{page.props.urlParams.match1}"`, keep every declared slot parameter present, and branch omitted/null, present-empty, matching, and no-match slots intentionally in SQL. Browser-test omitted query strings, empty slots, each slot matching while another slot does not, and all-slots-no-match states. For unbounded lists, use a target-verified bridge/normalizer that emits the exact scalar SQL params or reject the request.
- URL-delivered SQL-looking strings are safe only when they remain data bound through Named Query `Value` parameters or prepared calls. Do not concatenate decoded URL values into SQL, do not switch to QueryString parameters for user text, and do not treat URL encoding as SQL escaping. Encode quotes, semicolons, spaces, and comment markers for URL transport, then API/browser-test hostile-looking values against the exact binding path. In a direct `"{page.props.urlParams.matchText}"` to `displaypath LIKE :matchText` pattern, encoded values such as `Asset Alarm' OR 1=1 --`, `Asset Alarm'; SELECT 1 --`, and `Asset Alarm' -- comment` decoded and rendered as literal parameter values and returned 0 rows; they did not broaden or execute SQL.
- For Button or script-driven query-string navigation, use `system.perspective.navigate(url=...)` with a full Perspective client URL when the intent is to change `page.props.urlParams` and refresh dependent bindings. Do not pass `"/same-page?name=value"` as the positional `page` argument and assume it will refresh a mounted view's URL-param bindings; page navigation is for Perspective page paths, while query-string URLs belong in the `url` argument. This same URL-argument pattern can start on one source page and navigate to a different target query page: build the full target Perspective client URL, keep reserved characters URL-encoded, encode literal plus signs as `%2B`, encode literal `&` as `%26`, literal `=` as `%3D`, literal `#` as `%23`, and literal `%` as `%25` when they are part of a value, and bind the target page's Named Query parameter from `"{page.props.urlParams.<name>}"` or a target-verified bridge. Browser-test the click by verifying the target URL path/search, visible target title/content, visible `page.props.urlParams.<name>` echo, the direct or bridged value used by the Named Query param, row count/table state, expected row presence or absence, and relevant console errors; when `#` could appear, also verify `window.location.hash`, and when the target SQL uses `LIKE`, verify decoded `%` values against the row result instead of assuming URL encoding made them literal.
- If the requirement explicitly says to open a new browser tab, use the documented optional `newTab` argument, for example `system.perspective.navigate(url=<full client URL>, newTab=True)`, but verify separate-tab behavior in the actual target client/browser. A rendered target page proves the URL/query binding path, not that a distinct tab stayed open; the proof should capture browser tab/page state before and after the click, show the original page still available on the source URL, show a separate target tab with the expected path/search, and show target-side URL-param echoes plus query-backed row count/table state.
- Use explicit date/time range params for history, audit, alarm journal, and production reports.
- For date/time filters, do not assume URL/query-string strings, DatePicker values, Perspective DateTime Input `props.value`, epoch millis, and Named Query DateTime/Timestamp params coerce the same way. For direct `page.props.urlParams` filters, the conservative pattern is to bind the URL values into required Value/string Named Query params and normalize or cast in target SQL, such as `datetime(:startTime)`, `CAST(:startTime AS TIMESTAMP)`, `to_timestamp(:startTime, ...)`, or the target database's timezone-aware equivalent, unless target runtime proof already exists for DateTime/Timestamp params. For DateTime Input component filters, the conservative pattern is to bind `props.value` into a required Value param and normalize epoch-millis/text/null/invalid states in SQL unless the target proves DateTime/Timestamp metadata works. Prove broad/in-range, future/no-row, inverted/invalid, and null/empty states with `namedQueryPreview` plus visible browser echoes/status labels; page/view structure checks alone do not prove runtime date coercion. Treat unparseable date text as a first-class state because some target functions return `NULL` instead of throwing. Do not assume returned SQL date/time expressions arrive in Ignition as Java Date values: date/time functions can return text, epoch companions as integer-like values, Julian-style values as floats, and invalid/empty/null inputs as null companions depending on the database and driver. Return explicit companion columns such as `iso_timestamp`, `epoch_millis`, `parse_state`, and `source_timezone` or normalization-state fields; parse and format intentionally before Jython date math or UI display. Treat offset normalization, timezone behavior, and index/performance effects as target-specific until proven.
- For dynamic `IN` filters, do not pass an array, CSV string, or selected-value list into one Named Query `Value` param and expect it to expand. A predicate such as `displaypath IN (:matchCsv)` treats `matchCsv` as one scalar value; `<valueA>,<valueB>` is not the same as two placeholders and should return no exact match unless the database row literally contains that comma-separated string. Prefer a bounded placeholder shape such as `displaypath IN (:match0, :match1)` with one declared Value param per slot, or generate the placeholder list in trusted code from a validated value count. Handle empty lists before SQL, keep every declared slot present in API previews and Perspective bindings, and test exact-match, mixed match/no-match, all-no-match, empty, and null-slot states.
- For raw Jython `system.db.runPrepQuery`/`runScalarPrepQuery`/`runPrepUpdate`, pass params as ordered lists/tuples with one intentional value per `?` placeholder; use `[None]` for a SQL NULL placeholder instead of omitting that slot. Never pass scalar strings, numbers, dictionaries, or a list of parameter dictionaries. Validate placeholder counts before calling. Driver behavior is not portable: on the tested SQLite target, missing params via `[]` or `None` were accepted as SQL NULL while extra params failed and scalar/dict params failed coercion, but other drivers may reject missing params or bind differently.
- Do not pass secrets as query params.
- Validate enum-like params before they reach SQL.
- For host-runner previews of QueryString or Database Named Query params, reject them by default unless an exact allowlist is supplied, and require rejected values to fail before execution. For Database params, `allowDatabaseParameters` plus `databaseParameterAllowlist` is only a pre-execution guard: it authorizes a controlled attempt with an allowlisted connection name, not proof that Ignition substitutes a Named Query database placeholder.
- Treat Database `<Parameter>` Named Queries as target-specific. A reader can expose a synthetic `database` parameter when `attributes.database` is `<Parameter>`, but an allowlisted preview may still fail at runtime by looking for a literal `"<Parameter>"` connection. Verify dynamic database selection on the target Gateway before teaching or relying on it.
