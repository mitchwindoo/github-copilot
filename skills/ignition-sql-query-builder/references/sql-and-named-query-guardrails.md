# SQL and Named Query Guardrails

## Named Query First

- Prefer Named Queries for Perspective/database-backed pages instead of embedding SQL in view JSON or event scripts.
- Never assume a lab, tutorial, copied, or example Named Query path exists on another Gateway. Treat every concrete Named Query path, project name, database connection, table, and column in examples as a placeholder unless it came from the user's target, `namedQueriesList`/`namedQueryRead`, exported project files, or user-provided screenshots/configuration.
- Do not carry concrete Named Query paths forward from one-off local checks, prior sessions, lab/tutorial projects, or bundled examples into reusable output. Use placeholders such as `<namedQueryPath>` unless the path was discovered from the current target or supplied by the user.
- Use Value/Parameter params with `:paramName` for values.
- Avoid QueryString parameters by default. Use them only for explicitly allowlisted identifiers/fragments such as a vetted sort column, never for user-supplied values.
- Value params and prepared `?` placeholders cannot stand in for table names, column names, `ORDER BY` fields, sort directions, operators, or SQL syntax. For those fragments, map a user/UI key to an allowlisted SQL identifier and reject non-matches before execution.
- For a small fixed sort set, prefer a harmless `Value`/string enum key over a QueryString SQL fragment. Keep Dropdown `props.options[].value` entries as keys such as `time_desc` or `time_asc`, bind that scalar as a normal Named Query param, and choose among fixed SQL branches such as `ORDER BY CASE WHEN :sortKey = 'time_desc' THEN eventtime END DESC, CASE WHEN :sortKey = 'time_asc' THEN eventtime END ASC`. Reject or deliberately zero-match invalid keys before returning rows, API/browser-test every sort key plus a SQL-looking invalid key, and verify that the visible first row/order actually changes. Treat `CASE` ordering, null placement, collation, and index use as target-specific; for heavy queries, separate vetted Named Queries or trusted allowlisted code-generated fragments may be better.
- Avoid Database parameters unless the user has explicitly approved dynamic database selection and the target connection names are allowlisted.
- Keep database connection names as placeholders such as `<databaseConnection>` in reusable materials.
- When host API access exists, discover with `namedQueriesList`, inspect with `namedQueryRead`, and sample with `namedQueryPreview`; record API evidence in sibling testing/evidence notes, not in generated customer SQL.
- For runner/package work, list packaged Named Query resources in `dependencyNamedQueryPaths`, include raw `resource.json` and `query.sql` in the package, and validate the page with the same dependency list before relying on query-backed bindings. If raw `resource.json` is unavailable, bind to the existing target query path without listing it as a packaged dependency, or treat the copied query as structurally unproven until an applied `namedQueryPreview` succeeds.

## Dashboard Query Rules

- Bound preview/dashboard queries with a small numeric top-level `LIMIT`, `TOP`, `FETCH`, a narrow time range, or Named Query max return size. Keep the SQL row limit within the preview/API cap. Include the explicit outer bound even for synthetic or test rowsets built from `UNION ALL`.
- For pageable queries, do not bind raw UI, URL, Dropdown, TextField, or script text directly into `LIMIT`, `OFFSET`, `TOP`, `FETCH`, or page-size clauses. Normalize to integers first; clamp page size to an allowlisted maximum and offset to a nonnegative range; decide what zero, null, negative, float, invalid text, numeric strings, and oversized values should mean before binding. If runner preview or the database cannot prove a parameterized limit is bounded, prefer a literal maximum cap plus a row-window predicate or target-tested clamp pattern over raw `LIMIT :limitValue OFFSET :offsetValue`. On the tested SQLite target, raw dynamic `LIMIT/OFFSET` was read-only but not bounded-preview eligible; runtime accepted numeric strings, returned zero rows for zero limit, treated negative offset like zero, allowed negative/oversized limits to return the whole finite rowset, and errored on float, invalid, and null values.
- Select only needed columns and alias every returned expression to a unique, simple, Perspective-friendly name. Prefer `snake_case`; avoid duplicate aliases, spaces, hyphens/punctuation, and reserved words for fields consumed by Perspective tables, transforms, or helper dictionaries.
- Return rows as arrays of objects for Perspective tables; table `field` values must match returned column names exactly. If two returned columns have the same name, row objects or dictionaries can collapse one value, so fix the SQL aliases instead of configuring two table columns with the same `field`.
- For master-table-to-detail-query pages, return a stable helper key from the master query, such as `<asset_key>` or `<row_id>`, with a unique simple alias. Configure the helper key as a hidden Table column with `visible: false` when users should not see it; the official Table docs state hidden columns remain available to view params and selection. Enable row selection intentionally, bind the detail query param from `"{../<MasterTableName>.props.selection.data[0].<stable_key_column>}"`, and add a visible selected-key echo plus query-derived detail row-count/status label. Prove initial no-selection/null behavior, at least two selected rows, hidden-key availability, invalid/SQL-looking key handling, missing-param rejection, and unexpected-param rejection. Do not mistake static master table rows for proof that the selected-row detail query ran.
- Include deterministic ordering for recent-events/top-N displays.
- Handle zero rows as a valid state; build query-bound row-count/status labels and empty-state table or label fallbacks. If users need to understand the schema while no rows are returned, render a separate preview-column/status label from metadata instead of assuming an empty IA Table will show headers. Do not treat defensive default/fallback text as proof that the query returned zero rows; prove the exact parameter map with `namedQueryPreview` and inspect the binding parameters when required params are involved. Do not index row 0 until row count is positive.
- For aggregate Query-type rowsets, distinguish the rowset contract from aggregate value states. An ungrouped aggregate without `GROUP BY` can return one row even when the filtered input has no rows: `COUNT(*)` and `COUNT(<column>)` can be `0`, while `SUM`, `AVG`, `MIN`, and `MAX` can be SQL `NULL`. Grouped aggregates and `HAVING` filters can instead return zero rows while still preserving column metadata. For KPI labels, counters, and dashboard cards, return explicit companion fields such as `row_count`, `count_all`, `count_non_null`, `metric_value`, `metric_state`, and a deliberate `COALESCE(<metric>, 0)` display value only when zero is the intended default. Do not collapse SQL `NULL`, aggregate zero, and no returned group into one "no data" case.
- Preserve blank-sensitive values deliberately. Query-type rowsets can carry SQL `NULL`, empty strings, single-space strings, numeric `0`, `0.0`, and false-like numeric zero as distinct values even when Perspective table cells or transform truthiness make them look blank or false. When users must tell those states apart, return explicit companion fields such as `value_is_null`, `value_length`, `value_state`, `row_count`, or display markers/status labels; do not collapse valid zero values into "no data".
- Preserve exact numeric values deliberately. Query-type rowsets can carry large identifiers, 64-bit integers, decimal-like values, floating arithmetic outputs, and boolean expressions through different SQL, driver, preview JSON, Perspective, browser table rendering, and Jython shapes. When exact identity or display precision matters, return explicit companion fields such as `id_text`, `decimal_text`, `display_value`, `numeric_state`, `storage_type`, `scale`, or `source_unit`; bind those companions for user-facing table columns, labels, and exports instead of relying on generic client numeric formatting. Browser-rendered Perspective tables can format, round, use exponential notation, or add locale separators for numeric cells even when preview/runtime values look acceptable. Verify target preview/runtime cell types and browser-visible text before math, comparison, display formatting, JSON/client handoff, or claiming exact display.
- Treat preview rows as a sample, not complete production data.
- Prefer `--` line comments in generated SQL. If block comments are present, keep them balanced and non-nested; avoid `/* ... */` comments when comments may include tag paths, globs, regex, or text containing `/*` or `*/`, and do not place the only row bound after an uncertain block comment.

## Operator Action Logs

For custom Perspective button/action logging, prefer an append-only table or Named Query with stable forensic columns: timestamp, project, session, page id/path, actor, button key, event name, target path, previous value, new value, outcome, write quality, audit status, correlation ID, and optional JSON payload. Parameterize values, allowlist identifiers, index time/session/page/actor/button/correlation fields, and verify inserts with bounded readback. For Update Named Query action logs, require all declared params before calling `system.db.runNamedQuery(projectName, queryPath, params)` and verify one affected row or one durable row per action.
