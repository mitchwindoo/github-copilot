# Jython Database Runtime

## Jython Use

When scripting in Ignition 8.1/Jython 2.7:

```python
rows = system.db.runNamedQuery("<projectName>", "<namedQueryPath>", {"param": value})
```

Always pass one parameter dictionary/Map, even when it is empty (`{}`). Do not pass a list of parameter dictionaries. Validate required and unexpected keys before runtime or with `namedQueryPreview`; on the tested Query-type Value-param target, missing declared keys reached SQL as `NULL` and extra map keys were ignored, while a list container failed. In Gateway/Perspective reusable helpers, prefer the explicit `system.db.runNamedQuery(<projectName>, <namedQueryPath>, params)` shape; shorter no-project forms may resolve in some scopes but are ambiguous and can break transaction call shapes.

For Query-type rowsets, check preview columns or `getColumnNames()` for unique, simple names before converting rows to objects or dictionaries. Duplicate aliases are unsafe: index access can still expose separate physical columns, while preview row objects, name-based row access, and plain dictionaries can keep or overwrite different duplicate values. Avoid duplicate, spaced, hyphenated, punctuation-heavy, or reserved-word aliases in Perspective table fields, transforms, and helper dictionaries; fix the SQL aliases, preferably to unique `snake_case` names. Do not use `if value:` as an existence test for query cells because SQL `NULL`, `""`, `0`, `0.0`, and false-like numeric zero can all be falsey in Jython while needing different UI handling. Test `value is None`, string length, numeric equality, and row count explicitly, and add marker/status fields when blank, empty, null, and zero must be visually distinct. For exact numeric result cells, inspect types before arithmetic, formatting, dictionary/JSON conversion, or Perspective display: large integers can be integer-like while decimal-like, overflow, or computed values can be float/real-shaped or display with rounded/exponential text. Keep text/display companions for IDs, counters, exact decimals, and high-precision values. For date/time result cells, inspect types before `system.date` math; prefer explicit ISO text, epoch-millis, parse-state, and timezone/normalization companion fields instead of treating a stringified timestamp as a `java.util.Date`. For aggregate rowsets, check Dataset/PyDataSet row count before reading aggregate fields: a zero-row grouped or `HAVING` result is different from one ungrouped aggregate row where `count_all` is `0` and metric fields are `None`.

Keep Perspective event scripts thin. Put reusable query composition/validation in Project Library scripts or Named Queries.

For Update Named Queries, the default `system.db.runNamedQuery(<projectName>, <namedQueryPath>, params)` return is an affected-row count. Treat that count as a contract: expect `1` for a single-row insert/update/delete, `0` for a legitimate no-match update/delete, and investigate anything else. If the generated key matters, call with `getKey=1` as a keyword argument: `system.db.runNamedQuery(<projectName>, <namedQueryPath>, params, getKey=1)`. Do not leave empty positional slots, do not pass a list of parameter dictionaries, and do not rely on the no-project form in Gateway/Perspective helper code; it can be interpreted as the project argument and fail path resolution. Verify affected rows and generated keys with a follow-up readback on the target.

For Scalar Named Queries, the default `system.db.runNamedQuery(<projectName>, <namedQueryPath>, params)` return is a plain first-row/first-column scalar, not a Dataset/PyDataSet. Use this for single counters, `MAX`/`MIN` values, IDs, and compact status values. If SQL returns zero rows or first-column `NULL`, expect a `None`-like result and use a Query-type rowset with explicit companion columns such as `row_count`, `value_is_null`, or a sentinel when the distinction matters. Always pass one params dictionary/Map; a list is not a valid Named Query parameter container.

For prepared inserts/updates/deletes, `system.db.runPrepUpdate()` returns affected-row count by default. Treat that count as part of the contract: expect `1` for a single-row insert/update/delete, expect `0` for a legitimate no-match update/delete, and flag any other count before claiming success. Pass ordered params with one intentional value per `?` placeholder, use `[None]` for intentional SQL NULL values, and use `getKey=1` only when the target database, driver, table definition, and statement support generated-key retrieval. Prefer a keyword argument when available, confirm the returned key is nonblank and numeric/string-shaped as expected, and verify it with a follow-up `SELECT` before using it in downstream writes. For write probes or migrations, wrap the smallest useful batch in an explicit transaction, rollback during tests, and verify the row/table state after rollback or cleanup because DDL lifecycle, generated-key shape, and affected-row behavior are driver-specific.

For fixed standard-statement writes, `system.db.runUpdateQuery()` returns affected-row count by default and can return a generated key when called with `getKey=1`, if the target driver and statement support it. Use this only for trusted, fully composed SQL text; a `?` placeholder in `runUpdateQuery` is not a bound parameter slot. Prefer `runPrepUpdate` or Named Query `Value` params for any dynamic values. Keep the database connection explicit, pass a transaction id only in the `tx` position, and verify insert/update/delete counts, no-match counts, generated-key readback, rollback, and cleanup on the target before claiming a write workflow works.

For multi-statement writes, use `beginTransaction(<databaseConnection>, ...)`, keep the returned `tx` handle separate from the database argument, and close it in a `finally` path. The conservative prepared-call shape is `system.db.runPrepQuery(sql, params, <databaseConnection>, tx)`, `system.db.runScalarPrepQuery(sql, params, <databaseConnection>, tx)`, or `system.db.runPrepUpdate(sql, params, <databaseConnection>, tx)`. Keyword `tx=tx` and omitting the database argument can work on some targets, but the explicit database-plus-transaction form is clearer and more portable. Never pass the transaction handle in the database-connection slot, and never reuse a transaction after `closeTransaction(tx)`. Commit or rollback intentionally before close. For Named Query transactions in Gateway/Perspective scope, include the project first, check that the returned transaction id is not blank, and keep `tx` separate from params: `beginNamedQueryTransaction(<projectName>, <databaseConnection>, ...)` then `runNamedQuery(<projectName>, <namedQueryPath>, params, tx)`. The default transaction write return is still the affected-row count; `getKey=1` with the `tx` positional argument can return a generated key on supporting targets, but verify inside the transaction and then verify commit or rollback state. Do not use `runNamedQuery(<namedQueryPath>, params, tx)` in Gateway-scope transaction code; the transaction id can be treated as the params argument.
