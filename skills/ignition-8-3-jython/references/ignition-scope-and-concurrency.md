## Respect scope boundaries

- Verify that every `system.*` function is legal in the target scope before using it.
- Apply scope checks in this order: validate the exact execution scope and operation, verify the exact function's current Ignition 8.3 scope contract, confirm target availability, discover and validate named resources, obtain authorization for side effects, define completion/failure semantics, then satisfy any UI-thread rule. A callable attribute or familiar namespace never skips an earlier gate.
- Do not infer one scope for an entire `system.*` namespace. Perspective scripts execute on the Gateway rather than in a Vision Client, and the general Perspective page warns that client-scoped `system.gui` and `system.nav` functions do not work there. However, current per-function 8.3 pages explicitly list `system.file.readFileAsString` and `system.file.writeFile` for Gateway, Vision Client, and Perspective Session; in Perspective they operate on the Gateway filesystem. Verify the exact function page and target version instead of applying the older blanket `system.file` prohibition.
- Treat documented scope, runtime availability, authorization, and successful behavior as separate facts. The fixed matrix rejects `system.config.getResources` in Perspective even when an availability flag is true because its current function page is Gateway-only. Conversely, a documented scope still requires a target-availability check and does not prove that a resource, permission, argument, or operation result is valid.
- `system.util.invokeAsynchronous` is documented for Gateway, Vision Client, and Perspective Session and returns the executing Java `Thread`. The fixed Gateway action observed a different worker thread whose returned handle matched that worker, but the handle had no Future-style `get` result channel. Treat submission and a returned handle as neither completion nor success; provide an explicit bounded completion/result/failure channel owned by the caller or worker.
- A caller timeout is an observation boundary, not cancellation. In the fixed Java 17 matrix, `Future.get(1, MILLISECONDS)` raised `TimeoutException` while the task was neither done nor cancelled, and the same task completed normally after its gate was released. Track and reconcile late completion; do not automatically start duplicate work merely because the caller stopped waiting.
- Cancellation and interruption are cooperative. In the fixed running-task case, `Future.cancel(true)` returned true and the Future reported done/cancelled while the worker was still alive; the worker terminated only after it observed interruption and completed its bounded cleanup. A cancellation request, `isDone()`, or `isCancelled()` must not be reported as worker cleanup or side-effect completion unless the operation contract separately acknowledges that terminal state.
- When an interruptible wait raises `java.lang.InterruptedException`, its interrupt status has been cleared. Propagate the interruption or, when the boundary must finish bounded cleanup and return normally, restore it with `java.lang.Thread.currentThread().interrupt()` before exit. The fixed Future and `invokeAsynchronous` workers observed a real interrupt, remained alive during a controlled cleanup gate, restored the flag, and then terminated; this does not prove that arbitrary I/O or third-party code is interruptible.
- Observe asynchronous failure through the defined channel. The fixed Java Future surfaced a worker `IllegalStateException` only through `get()` as `ExecutionException`; the `invokeAsynchronous` `Thread` supplied no equivalent result retrieval. Catch only expected worker failures at the owned boundary, record a bounded sanitized terminal result, and preserve Python control-flow and Java-error propagation rules.
- Never use `Thread.stop`, `Thread.suspend`, unbounded `join`, spin loops, or a module-global flag as a generic cancellation design. Bound every wait by the shared deadline, keep per-invocation state local or synchronize an explicitly shared structure, release owned latches/executors in `finally`, and verify termination without blocking a UI or event-dispatch thread.
- Do not touch Vision components from an asynchronous worker; marshal the smallest component update back through `system.vision.invokeLater`, whose documented scope is Vision Client only. Do not pass a live request, session, component, or other scope-owned object across threads unless its exact API contract permits that lifetime and access.
- Current 8.3 pages list `system.tag.readBlocking` and `system.tag.writeBlocking` for Gateway, Vision Client, and Perspective Session. This scope listing is not a path, provider, permission, quality, completion, or write-success guarantee; retain the skill's discovery, authorization, per-result, and qualified-readback gates.
- Treat filesystem paths and returned file contents as resource/data-release boundaries. Validate a fixed or explicitly supplied path under the application contract, bound bytes/text, and avoid returning sensitive content. Require explicit authorization, backup/replace semantics, post-write verification, and cleanup before a file write even when the function is documented for the scope.
- The fixed 28-case scope matrix covers seven example operations and three named scopes. It proves the decision order and stable classifications in the tested runtimes, not every Ignition function, Designer Console behavior, actual API execution, permission, resource, UI-thread state, or external side effect. When current general and per-function documentation conflict, prefer the exact function contract, record the discrepancy, and run a focused target test before claiming behavior.
- Treat Gateway event, tag-event, message-handler, Java-callback, and asynchronous executions as potentially concurrent. Keep per-invocation state local, do not use unsynchronized module globals as a work queue or lock, and do not pass request/session/UI objects across threads unless the documented API permits it.
- Identify the event family before writing its handler. A project-scoped Gateway Tag Change script uses `newValue`, `previousValue`, `initialChange`, and `executionCount`; a tag-attached Value Changed script uses `currentValue`, `previousValue`, `initialChange`, and `missedEvents`. Do not interchange those names or infer one event family's lifecycle rules from the other.
- Treat `initialChange` as a lifecycle signal, not automatically as a business transition. Define whether the application initializes, reconciles, or ignores on that path before any side effect. For a tag Value Changed overflow (`missedEvents`), do not apply an incremental delta from only `previousValue` and `currentValue`; reconcile from an authoritative bounded source. Validate the relevant `QualifiedValue` quality and timestamp before acting.
- Project library or event-script changes can restart Gateway event scripts and reset `executionCount`; never use that count as a durable event ID, replay key, or cross-restart order. Keep external effects idempotent or use the tested durable claim/readback pattern. An in-memory/module-global set, counter, cache, flag, or lock is neither restart-durable nor cluster-wide merely because it appears to persist during one run.
- Make Gateway Startup scripts idempotent because project restarts can invoke them repeatedly while editing or deploying. Treat Shutdown scripts as best-effort cleanup, not a guaranteed finalizer: abrupt power loss or a hard restart can skip them. Use Update script `resources`/`manifestChanged` only through a bounded validated policy; do not execute code or choose unrestricted resources from their names.
- A tag-attached Tag Event Script can call project-library code only from the configured Gateway Scripting Project. Read UDT parameters at the event boundary when current values matter; do not cache them indefinitely. Gateway Tag Change scripts can run on separate threads, so synchronize genuinely shared in-memory structures while still treating them as non-durable and non-cluster-wide.
- Define a tag event as an application delivery contract before producing an effect: exact tag path, event family, stable logical event ID, normalized business fingerprint, current/previous `QualifiedValue` policy, durable claim states, completion record, and authoritative reconciliation read. `executionCount`, timestamp alone, or an in-memory set is not a durable event identity.
- On `initialChange`, `missedEvents`, unacceptable quality, missing/unacceptable previous value, non-increasing timestamps, a stale observation, or a same-timestamp/different-value conflict, stop incremental processing and enter a bounded application-specific reconciliation path. Do not manufacture or replay the skipped transitions from the two endpoint values. Validate an authoritative `readBlocking` result's exact count, path mapping, quality, value, and timestamp before updating a checkpoint or declaring convergence.
- Suppress a completed, in-progress, conflicting, or outcome-unknown duplicate before the effect. If the effect occurs but recording completion fails, retain `outcome_unknown`; a later project startup must reconcile it rather than replay it. A fresh startup must compare durable checkpoints with bounded authoritative reads and must work safely even when all module globals are empty. The fixed adapter proved these branches only in memory; it did not run a tag event, restart a project/Gateway, call `readBlocking`, or prove a real store/effect atomic.
- Keep shutdown-independent correctness. Because abrupt loss can skip Shutdown, durable claims/checkpoints and reconciliation must not depend on a final module-memory flush. Do not claim exactly-once behavior unless the real durable claim and external effect share a tested atomic/idempotency mechanism across every processing location.
- Keep project-library top level limited to imports, constants, and lightweight function/class definitions. Current Ignition 8.3 documentation says the library body runs to create definitions under several conditions and that statements outside functions/classes execute too. Do not open connections, start threads/timers, register handlers, perform writes, or launch application work at import time.
- Keep the project-library dependency graph acyclic. Extract shared contracts into one lower-level module or inject the dependency; never rely on import order or a partially initialized module to make a cycle work. In the fixed live two-module cycle, Ignition repeatedly re-entered both module bodies until the fixture's 12-record guard stopped the sequence.
- Treat project-library import failure as a dependency-or-initialization failure until classified, not automatically as a missing module. In the fixed live loader, both a top-level `RuntimeError` and the circular import surfaced to the caller as `ImportError`, while the failed module name still appeared module-present. Require an exact ready marker or required-member check before use, and log only a bounded sanitized classification.
- Make every unavoidable top-level operation idempotent and known-safe to repeat. Two explicit imports of the fixed failing live module executed its top level twice before failing. Do not add an automatic import retry or infer known-no-effect from the exception type.
- Do not use `sys.modules` presence, deletion, or `reload()` as a Project Library readiness, diagnosis, or recovery contract. The fixed Ignition loader differed from the fixed standalone Jython core loader on failed-module visibility and circular re-entry. Fix the resource and dependency graph, save or import the corrected project, then use one bounded exact-generation/readiness probe. The fixed corrected phase recovered and a second successful import was cached, but that observation proves only the tested project and generation.
- Treat module globals as one loaded-generation cache only. In the fixed live module, two calls after one project import observed atomic counts 1 then 2; after importing a changed generation, the first call observed the new generation at count 1. This proves neither a documented lifetime for every module/scope nor durability across another save, project/Gateway restart, JVM replacement, or cluster node.
- Do not assume a whole-project import invalidates every unchanged project-library module. After the fixed helper changed, its first phase-B count was 1; a later import that changed only the Web Dev GET resource left that helper generation loaded and its next count was 2. In a separate live resource-rename test, adding and removing Project Library resources reset the unchanged, byte-identical helper's in-memory state. These observations prove no general cache contract: tie readiness to an explicit generation/resource contract and make both state loss and state retention safe.
- Synchronize mutable module state when concurrent calls genuinely share it, but do not confuse thread safety with durability or distributed coordination. The fixed `AtomicLong` only proves its counter sequence in one tested project-library module. Prefer per-invocation state; use an explicitly bounded cache only when loss/rebuild is safe, and use a durable atomic store for correctness state.
- Treat project-import/save acknowledgement and live-code readiness as separate states. One immediate post-import GET still reported API v0.34.0 before a later bounded probe reported v0.35.0. After deployment, rediscover the exact version/action or application generation with one shared deadline before tests or traffic; do not use fixed sleeps or assume HTTP success means every route already serves new code.
- Treat a Project Library resource rename or removal as a contract migration, not a cache-refresh technique. Update every caller and imported member, deploy the corrected resource graph, then use one bounded exact readiness probe that verifies the old name is absent and the replacement name, required members, and expected generation are present. Do not use `reload()` or `sys.modules` manipulation as deployment logic.
- Do not assume a project import cancels, migrates, or updates already-running work or references captured from the old generation. In the fixed live overlap test, one bounded Web Dev request captured the old module, function, and object, then returned their old `"new"` generation after a project import renamed that resource to the `"final"` generation; a fresh request saw the old name absent and only the replacement generation. This proves only that exact request/project/import path, not every scope, worker, object, or loader. Bound work, carry an immutable generation through the operation, and use an application-specific drain/fence plus idempotent reconciliation when mixed-generation effects would be unsafe; do not automatically duplicate work after deployment.
- Treat removal or renaming of a function, class, method, or constant inside an unchanged Project Library resource as an API-breaking caller migration. Inventory both deferred lookups such as `module.member` and early bindings such as `from module import member`, stored callbacks, bound methods, class references, and long-running objects. Prefer an additive compatibility phase when practical; remove the old member only after updated callers and the application-specific old-generation drain/fence are verified.
- Distinguish a captured callable from later attribute lookup. In the fixed Jython matrix, a captured function and bound method still ran after their module/class attributes were deleted, while later lookup through the same module and object raised `AttributeError`. This is ordinary fixed Jython behavior, not an Ignition loader guarantee, and it does not make the removed member available to new callers.
- Gate a member-removal deployment with a fresh request-context probe of the exact generation and required member set. In the fixed live Ignition update, a fresh request saw the new kept function/method, `AttributeError` for removed module/object attributes, and `ImportError` for `from ... import removed_function`; one already-running Web Dev request retained its old module, function, class, object, and bound-method paths through the same update. Do not use a previously imported module, stored callback, or successful old invocation as readiness proof. Do not classify every `ImportError` as a missing member; top-level and dependency failures can use the same exception boundary.
- Treat a Project Library function or method signature change as an API migration even when its name remains unchanged. Inventory positional arity/order, keyword names, added or removed defaults, `*args`/`**kwargs`, stored functions and bound methods, Java callbacks, event handlers, scheduled work, and every direct caller. Prefer a tested additive compatibility wrapper or a versioned new function name; broad `*args`/`**kwargs` shims can hide invalid calls and must validate an exact documented contract.
- Never implement signature migration as `try: old_call(...)` followed by `except TypeError: new_call(...)`. A `TypeError` can originate inside the callee after an effect has begun, so retrying can duplicate work and misclassify an application failure as signature detection. Select the contract through an explicit version/capability/generation gate before the call.
- Do not use one successful positional call as readiness proof. In the fixed live old generation, the new three-positional-argument call also succeeded because its values fit the old arity; after the update, a same-arity positional reorder changed `left>right` to `right>left` without raising. A fresh exact-generation probe must exercise discriminating keyword/default cases and verify the required output contract, not merely callable existence or one compatible positional result.
- Expect old signature contracts to coexist with a fresh new generation during bounded overlap. In the fixed same-resource Ignition update, one in-flight Web Dev request retained the old module, function, class, object, bound method, defaults, and keyword names, while a fresh request used the new signature and rejected old omitted/default and keyword calls with `TypeError`. This proves only the tested Ignition 8.3.8 Web Dev/project-import path; use an application-specific drain/fence and idempotent reconciliation when mixed-signature effects are unsafe.
- Treat a Project Library return-type or return-schema change as an API migration even when the callable name and parameters are unchanged. Define the exact top-level type, required and allowed keys, schema/generation marker, field types/null policy, status/quality/completeness rules, expected count, item identity/order, and error/effect meaning. Decide explicitly whether unknown keys are rejected or allowed as documented extensions.
- Validate the return contract before truthiness, `None` checks, `len`, iteration, indexing, unpacking, serialization, or effects. In the fixed live migration, an old error/missing result was falsey `None`, while the new error envelope was truthy and the new missing envelope contained `value: None` but was not itself `None`; the old partial list had length 1 and iterated an item, while the new partial envelope had length 7, iterated field names, and integer index `0` raised `KeyError`. These are exact tested cases, not universal dictionary values.
- Keep value presence, status, quality, completeness, and expected/result counts independent. A non-empty partial item list is not complete success, and a present value does not override unacceptable quality. The fixed return-contract fixture uses quality strings only to test consumer discipline; it does not establish behavior for Ignition `QualityCode` objects or which real subcodes a specific application may accept.
- Prefer an additive versioned function/schema or an explicit preselected adapter during return-contract migration. Never call one parser and then catch `KeyError`, `TypeError`, or `IndexError` to retry another schema: those exceptions can arise from real application data or after an effect begins. Select the schema through an exact version/capability/generation gate and verify a discriminating output shape before traffic.
- Expect old and new return shapes to coexist during bounded deployment overlap. In the fixed same-resource Ignition 8.3.8 test, one in-flight Web Dev request retained its captured old module/functions and returned old list/`None` shapes after phase B was live, while a fresh request returned the new exact envelopes. This proves only that tested Web Dev/project-import path; drain or fence old consumers and use idempotent reconciliation when mixed return semantics could cause unsafe effects.
- Treat callback or event-handler registration as an owned lifecycle contract, not as a side effect of assigning a Project Library function. Define the registrar identity and scope, stable registration ID/token, event/filter, callback generation/signature/return/effect contract, duplicate policy, generation-checked replacement and unregister rules, admission fence, queued/in-flight drain, deadline, cleanup, and reconciliation before deployment.
- Make same-ID/same-generation registration idempotent. Make same-ID/different-generation registration conflict until an explicit expected-generation replacement succeeds. Do not register a new callback and assume the old one disappears: duplicate delivery can duplicate effects. Do not treat deleting a module member, dropping a local reference, or importing a new project generation as unregister proof.
- Unregister by the registrar's exact ID/token and expected generation when the real API supports those operations. Removal from the registry does not invalidate a callback already captured or executing: the fixed in-memory contract invoked a held old callable after exact replacement and after registry removal. If a registrar lacks inspect, deduplication, replacement, unregister, or drain semantics, keep migration unproven and use only an application-specific adapter/dispatcher whose behavior has been tested.
- Gate callback readiness from a fresh request/execution context by inspecting the exact registrar state, registration ID, generation, and a discriminating callback result. In the fixed authenticated Ignition 8.3.8 overlap test, a fresh Web Dev request replaced the stored callback from `old` to `new`, while the already-running old request retained its held callback and observed `old` through both its captured globals dictionary and a new `system.util.getGlobals()` call. This proves only the tested Web Dev/project-import/globals seam; it does not reveal a universal loader or registrar implementation.
- Treat `system.util.getGlobals()` as a legacy JVM-lifetime dictionary, not as a durable production callback registry or fresh-readiness oracle. It does not prove persistence across Gateway restart, redundancy switchover, or cluster nodes. The fixed globals key was a controlled test seam and was removed by an explicit idempotent cleanup action; project import/save was not cleanup.
- Fence legacy callback admission, drain or bound queued and in-flight delivery, and reconcile outcome-unknown effects before declaring migration complete. Never catch a callback exception and retry the old or new generation merely to detect which contract applies; select the generation before invocation, because the first callback may already have produced an effect.
- Treat project and component messages as validated asynchronous boundaries. A payload is not safe merely because it is a `dict`: define the exact required and allowed top-level keys, per-field types, null policy, item-count limits, text-length limits, duplicate policy, and nested-value policy, then validate all of them before work begins. Choose the message scope explicitly instead of accepting broad defaults.
- Account for Python 2's Boolean/integer relationship when validating numeric fields. In the fixed message-contract matrix, `isinstance(True, int)` was `True`; a sequence field that prohibited booleans therefore used `type(value) in (int, long)` and rejected `True` with `invalid_sequence_type`. Use exact numeric types or an explicit Boolean rejection only when the field contract requires it; do not turn this fixture-specific choice into a rule for every API.
- If a message field is limited to JSON-safe scalars, accept only the scalar types named by that contract and require floats to be finite. The fixed matrix rejected nested list/dict values, NaN, infinity, oversized text, duplicate paths, unknown keys, missing keys, and out-of-range counts with stable bounded codes. Some encoders accept non-finite spellings, but that does not make them strict portable JSON values.
- Keep limits tied to the actual payload contract. The tested example used 64 characters for `eventId`, 16 items, and 256 characters for paths and text values; those numbers prove the fixture, not suitable limits for every message. Set and test application-specific bounds instead of copying them blindly.
- Return stable validation codes and bounded counts; do not echo the raw payload or unrestricted exception text by default. Validation and a successful send establish only payload acceptance and routing, not asynchronous handler completion. Define completion, timeout, replay, duplicate-delivery, and idempotency behavior as separate contracts.
- Do not claim exactly-once processing from a successful `sendMessage` call, a local lock, an unsynchronized or synchronized module-level set/dict, or a check-then-write sequence. Those mechanisms do not by themselves prove one atomic durable decision across concurrent executions, project-script restarts, or every Gateway node that can process the logical event.
- Define a stable logical event ID and a fingerprint computed from the normalized business fields that determine the operation. Do not trust a caller-provided fingerprint as proof of payload identity. Treat the same event ID with a different fingerprint as a conflict and stop before the side effect.
- Before processing, require one durable atomic claim shared across every relevant execution location. Use explicit states such as `in_progress`, `completed`, known no-effect failure, and `outcome_unknown`, with a bounded attempt count. A completed, in-progress, conflicting, attempt-limited, or outcome-unknown claim must not be processed again by default.
- A known no-effect failure may become retryable only when its contract proves that no effect occurred, the caller explicitly authorizes retry, the attempt bound and shared deadline permit it, and the same event ID/fingerprint are retained. Do not implement an internal automatic retry loop merely because the state is named retryable.
- Once the processor is called, an exception does not prove that no effect occurred. Classify a processor exception, invalid processor result, or successful processing followed by failure to durably record completion as outcome unknown; make one bounded attempt to record that state, preserve the primary failure if recording also fails, and do not automatically replay.
- A successful claim is not an exactly-once guarantee. Close the effect-versus-completion-record crash window by atomically committing the durable idempotency record with the local database effect, by sending the same idempotency key to a downstream operation that enforces it, or by using an explicit readback/reconciliation design. Handle stale `in_progress` leases through a tested expiry and reconciliation policy, not immediate replay.
- The fixed idempotency matrix used a 64-character lowercase hexadecimal fingerprint, a 64-character event ID, a 128-character receipt, and at most five attempts only as example-contract limits. Its 27 injected cases prove adapter branching and call order in the tested runtimes; they do not prove that a real store is atomic, durable, restart-safe, cluster-wide, or coordinated with an external effect. Test those properties separately before relying on them.
- Keep per-session Perspective parameters in session/page/component state rather than a shared tag.
- Use `system.config` only in Gateway scope. Start discovery with `getActiveMode`, `getModes`, `getResourceTypes`, `getResources`, and `getResource`; use documented keyword arguments such as `moduleId`, `typeId`, and `name`. Treat `None` active mode and an empty modes list as valid states.
- Call `getResources` with both keyword arguments, for example `system.config.getResources(moduleId="ignition", typeId="database-connection")`. For a named resource, pass `moduleId`, `typeId`, and `name` to `getResource`. When the request is configuration inventory, do not substitute a similarly named runtime-status API such as `system.db.getConnections`; it has a different contract.
- Read safe `PyResource` metadata as properties. The tested pattern is bounded iteration followed by `unicode(resource.name)`; `resource.enabled` and presence of `resource.signature` also worked. Do not rely on `getName()` or stringify the whole object, and do not access `config` or `files` unless the task explicitly requires and authorizes them.
- Keep configuration discovery bounded and return only required metadata. Do not return resource configuration, files, or possible secret-bearing values by default.
- Treat `system.secrets` as an Ignition API boundary, not a Jython 2.7.4 feature. The fixed Gateway-scope probe found all eight documented names, including the three functions added in Ignition 8.3.8: `createEmbeddedSecretConfig`, `createReferencedSecretConfig`, and `readConfiguredSecretValue`. Availability does not prove provider configuration, permission, argument, or read behavior in another scope.
- Do not pass plaintext directly to `createEmbeddedSecretConfig`; its documented input is the JSON produced by the encryption service. A referenced config requires an explicitly discovered provider and secret name. Do not guess either identifier or expose them in routine logs.
- Treat `readConfiguredSecretValue` as a plaintext-release boundary. Call it only when the authorized task requires the value, keep the returned `PyPlaintext`/string lifetime and scope minimal, and never print, log, serialize, cache, return through Web Dev/message responses, place in component properties, or include it in exception text. Prefer passing a SecretConfig into an API that accepts it over materializing plaintext in Jython.
- Keep UI-only calls out of Gateway-scoped scripts.
- Keep long-running or blocking work off UI and event-dispatch threads.
- Make event handlers safe for retries and duplicate delivery when practical.
- Bound loops, waits, queries, and returned data sizes.
- Use `system.util.getLogger` with one stable, low-cardinality, period-separated name for each subsystem or operation family. Do not place request IDs, tag paths, usernames, device names, or other per-event values in the logger name; put an approved non-sensitive correlation ID in the bounded message instead. Current Ignition documentation says same-name loggers are shared and period-separated names support hierarchical filtering.
- Choose severity from a fixed application policy, not caller input. Use `debug`/`trace` for diagnostic detail, `info` for noteworthy normal events, `warn` for an undesired condition that does not stop the operation, and `error` for an unexpected runtime failure. Reserve `fatal` for the severe termination meaning documented by Ignition; do not label routine validation or recoverable failures as fatal merely to make them visible.
- Check `logger.isDebugEnabled()` or `isTraceEnabled()` before building an expensive diagnostic. The fixed adapter made zero builder and logger calls when debug was disabled and exactly one of each when enabled. The embedded fixed logger reported info enabled and debug/trace disabled at test time, but logger levels are mutable operational state; never hard-code those observed values.
- Keep the diagnostic schema exact, stable, and bounded. Prefer fixed fields such as a stable code, operation, outcome, approved correlation ID, attempt, duration, and item count. Reject newline/control characters and unknown fields rather than allowing log forging or arbitrary message expansion. The fixture's 256-character message, five-attempt, 600000-millisecond, and 1000-item limits are example-contract values, not universal logging limits.
- Exclude secrets, plaintext secret values, credentials, authorization headers, raw payloads, full URLs/query strings, filesystem/tag/resource paths, unrestricted values, and raw exception messages by default. Log only the minimum stable code and separately validated type/summary fields needed for operations. Validation cannot prove that a caller-chosen correlation ID is non-sensitive; make that an explicit producer contract.
- Treat Python `%` message construction and Logger `infof`/`warnf`/other `...f` calls as different formatting contracts. Current Ignition documentation says the `...f` methods use Java Formatter syntax. Keep the format string fixed in code, validate arguments, and never accept a caller-provided format string.
- Do not let a secondary logging failure replace the primary operation result. When the boundary requires containment, catch only expected ordinary Python and Java logger failures, return or attach a stable family/type without exception text, and preserve the primary outcome. The fixed adapter contained Python `RuntimeError` and Java `IllegalStateException` but still propagated Python `SystemExit` and Java `AssertionError`.
- Treat `system.util.setLoggingLevel` as an operational configuration change, not ordinary application behavior. Do not change levels from event code merely to force a message through; require explicit authorization, record the prior/desired scope, and restore or document the temporary change. Logger output destinations and level settings depend on execution scope, so verify the exact Gateway, Perspective, Vision, or Designer location instead of relying on `print` behavior.
