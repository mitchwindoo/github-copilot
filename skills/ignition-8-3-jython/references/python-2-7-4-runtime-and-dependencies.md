## Enforce Python 2.7 language guardrails

- Reject Python 3-only syntax. The maintained gate raised `SyntaxError` for 29 fixed forms: f-strings; `async def`, `async for`, `async with`, `await`, and async comprehensions; variable/function annotations and type-alias/type-parameter syntax; `nonlocal`; `yield from`; keyword-only and positional-only parameters; repeated positional call unpacking; dictionary, set, tuple, and list literal unpacking; starred assignment targets; assignment expressions (`:=`); `match`/`case`; `except*`; exception chaining with `raise ... from`; parenthesized `with` items; parenthesized decorator expressions; matrix multiplication (`@`); and numeric separators such as `1_000`.
- Do not reject valid Python 2.7 syntax merely because it differs from Python 3. The 25 acceptance controls preserve the earlier dict/set comprehensions, `from __future__ import print_function`, `except Exception as error`, `with`, `str.format`, and ordinary `*args`/`**kwargs`, plus fixed Python 2 recognition and semantic-review forms. Compilation of backticks, comma exception/raise syntax, `<>`, legacy octal, print statements, or tuple parameters proves recognition only; it does not recommend generating those legacy spellings. Prefer the clearer already-tested alternatives unless the exact task requires otherwise. A future import must remain at the beginning of its module, after only the module docstring.
- The maintained syntax gate contains 29 invalid and 25 accepted cases. The complete matrix matched in direct standalone Jython 2.7.3/2.7.4 and installed Ignition Jython 2.7.4 launches on the tested Java runtimes; the earlier 17-invalid/7-valid subset also passed the last audited embedded action. The 12 added rejection and 18 added recognition/review cases have not run through the embedded Gateway action. Treat all of them as bounded Python 2 compatibility guardrails, not as language features added by 2.7.4 or as a complete grammar proof.
- Remember that `bytes is str` in this runtime, while `unicode` is distinct. Use `basestring` when either text type is accepted, and perform explicit encoding/decoding at byte boundaries.
- Keep internal human-readable text as `unicode`. Decode incoming `str` bytes once with the source contract's explicit encoding, and encode `unicode` once with the destination contract's explicit encoding only when that destination requires bytes. Do not pre-encode for an Ignition/Java API that expects text.
- Do not use `str(non_ascii_unicode)` or `unicode(non_ascii_bytes)` as an encoding conversion. In the fixed matrix, those calls failed under standalone ASCII but succeeded under the embedded Gateway's UTF-8 default. Use `text.encode("utf-8")` and `wire_bytes.decode("utf-8")` (or the protocol's documented codec) and handle `UnicodeEncodeError`/`UnicodeDecodeError` according to the caller contract.
- Do not concatenate, join, or `%`-format a mixture of `unicode` and non-ASCII `str` bytes. All five fixed implicit operations failed under standalone ASCII and succeeded under embedded UTF-8, so success in the Gateway is not a portable contract. Normalize every operand to `unicode` before text composition; encode only the completed value at a byte boundary.
- Never use `reload(sys)`/`sys.setdefaultencoding(...)` to make implicit conversions pass. `sys.setdefaultencoding` was absent in all three fixed runtimes, and changing a process-wide default would hide boundary errors rather than define the source/destination codec.
- Treat `range()` as an eagerly created `list`, not Python 3's lazy range. Keep counts bounded; use `xrange()` when a lazy Python 2 sequence is appropriate.
- Treat `dict.items()` as a new `list`, not a Python 3 view. Avoid materializing an unbounded mapping merely to iterate it.
- Treat `map()`, `filter()`, and `zip()` as eager list-producing Python 2 built-ins, not Python 3 iterators. The fixed `map(None, [1, 2], [3])` case also padded the shorter input with `None`; keep inputs bounded and prefer an explicit loop when padding would be surprising.
- Use Python 2's `__builtin__` module name when direct built-in introspection is genuinely required. The fixed `builtins` import raised `ImportError`, while Python 2 names such as `basestring`, `cmp`, `execfile`, `file`, `long`, `raw_input`, `reduce`, `unicode`, and `xrange` were present.
- Do not infer Python 3 from one familiar built-in name. The fixed 142-name surface was identical in standalone Jython 2.7.3, standalone 2.7.4, and embedded 2.7.4; `print` appeared in all three, while `ascii`, `breakpoint`, and `exec` were absent. This comparison found no built-in added by the 2.7.4 upgrade.
- Account for both `int` and `long` where an arbitrary-size Python integer is valid; the fixed long literal has runtime type `long`.
- Define reusable classes as new-style classes with `(object)` and call `super(CurrentClass, self)`. The fixed two-argument call worked; zero-argument `super()` raised `TypeError`.
- Never use a mutable list/dict/set as a reusable function default. The fixed default list retained the first call's value on the second call. Use `None`, then create a new object inside the function.
- Do not assume a Python 3 standard-library module or third-party package exists because its syntax is familiar. Discover imports on the target Gateway and choose a verified Python 2/Jython-compatible implementation through an explicit deployment or configuration contract.
- Use the tested Python 2 module spellings when those APIs are required: `Queue`, `ConfigParser`, `SocketServer`, `BaseHTTPServer`, `SimpleHTTPServer`, `CGIHTTPServer`, `httplib`, `urllib2`, `urlparse`, `copy_reg`, `thread`, `StringIO`, and `xmlrpclib`. The fixed imports and bounded Queue, ConfigParser, URL, HTTP-object, and SocketServer cases passed in standalone 2.7.3, standalone 2.7.4, and embedded 2.7.4.
- Do not substitute the tested Python 3 spellings `_thread`, `configparser`, `copyreg`, `http.client`, `queue`, `socketserver`, `urllib.parse`, `urllib.request`, or `xmlrpc.client`; every fixed import raised `ImportError` in all three runtimes. This is a Python 2 baseline, not a 2.7.4 change. A separately installed compatibility package can change a target environment, so verify rather than generalize beyond the matrix.
- For this fixed Jython 2.7.4 target, import the verified Python 2 module directly. Do not emit a silent Python 3/Python 2 chain such as `try: import queue` followed by `except ImportError: import Queue`; it adds an unsupported branch and can hide a different import failure.
- Do not use one `except ImportError` around import plus initialization or member use. In the fixed three-runtime matrix, an absent module, an absent member of the importable `Queue` module, and a nested missing import all reached `ImportError`; the recorded errors had no `.name` or `.path` field. The broad handler selected a fallback even while the primary module was importable. Do not parse exception text to guess which site failed.
- Separate module import from capability validation. Import the exact required module, then validate each required member with `getattr(module, name, sentinel)` or an equally explicit fixed check before work begins. If the requirement is absent, return or raise a bounded stable dependency error rather than silently substituting an unrelated module.
- When two implementations are genuinely supported, choose between them through an explicit deployment/configuration contract and validate the selected implementation's required members before use. Do not select a backend solely because another import raised `ImportError`; target loaders, project-library modules, Java packages, optional installations, and import hooks remain environment-specific.
- Never invent an optional/vendor module identifier or required member name. If the exact installed identifier and contract were not supplied or discovered in the target scope, keep that branch disabled and return a stable `dependency_unconfigured`/unsupported result before import. A fake module or injected loader used by an in-memory test is a test seam, not evidence for a production import name.
- Do not emit modern methods merely because the surrounding expression parses. The fixed three-runtime matrix found no `str`/`unicode` `removeprefix`, `removesuffix`, or `isascii`; no `int`/`long` `to_bytes` or `from_bytes`; no `list.copy`; no `datetime.timezone`, `datetime.datetime.fromisoformat`, or `datetime.datetime.timestamp`; no `os.fspath` or `os.PathLike`; no `functools.lru_cache`; no `math.isclose` or `math.prod`; no `subprocess.run`; no `collections.abc`; and no `dict.__or__`. Fixed dictionary merge with `left | right` parsed but raised `TypeError`.
- Use a tested Python 2 alternative only when its narrower contract fits: non-empty `startswith`/`endswith` plus slicing for prefix/suffix removal; a bounded `all(ord(character) < 128 ...)` check after `basestring` validation for ASCII; `list(value)` for a shallow list copy; `source.copy()` plus `update()` for a shallow dictionary merge; exact-format `datetime.datetime.strptime`; and a bounded explicit multiplication loop. The fixed alternatives preserved their sources and returned identical results in standalone 2.7.3, standalone 2.7.4, and embedded 2.7.4.
- Treat protocol bytes, numeric comparison, caching, paths, dates/time zones, and process execution as separate contracts. The fixed `struct.pack(">I", 258)` result only proves one unsigned 32-bit big-endian encoding; the explicit closeness check only covered finite values with stated tolerances; `collections.Iterable` was tested only with a Python list; and no process or filesystem operation was performed. Prefer scope-correct Ignition or Java APIs after focused target verification rather than inventing a general replacement.
- The selected Python 3 API absences are a Python 2 baseline, not a 2.7.4 change. Attribute/import absence is not a complete API inventory, and a separately installed backport or compatibility layer can change a target environment; discover before relying on either absence or availability.
- Do not infer a standard-library expansion from the 2.7.4 upgrade. On the fixed Windows standalone distributions, `pkgutil.iter_modules()` exposed the same 227 top-level names in 2.7.3 and 2.7.4, and `sys.builtin_module_names` exposed the same 41 names. This is a discovery-surface comparison, not proof that every module imports or behaves identically.
- Do not treat a standalone Jython distribution as an exact inventory of Ignition's embedding. The fixed Gateway exposed 226 of those 227 top-level candidates; `ensurepip` was the one missing candidate, while the 41 built-in module names matched. Do not bootstrap or run pip inside the Gateway. Use an approved pure-Python dependency or JVM library only after testing it in the target scope.
- The tested Gateway did not discover the selected modern names `asyncio`, `builtins`, `concurrent`, `dataclasses`, `enum`, `pathlib`, `statistics`, `typing`, or `venv`. A later installation or backport can change name availability, so discover the target environment and do not use a name's presence as proof of Python 3 semantics.

## Triage a 2.7.3 to 2.7.4 migration

- Keep the Python 2 compatibility gate unchanged. The fixed syntax, Python 2/Python 3 module-name, selected modern-API, built-in, and standalone discovery matrices found no Python 3 expansion in 2.7.4. Do not relax a guardrail merely because the runtime version increased.
- Re-test every Java call with fixed-arity and varargs overloads. The fixed fixture changed from a varargs selection in 2.7.3 to the compatible fixed-arity method or constructor in 2.7.4, and two overlapping-varargs signatures selected different branches. Prefer an explicit wrapper with one verified signature when practical.
- Re-test Java `char` boundaries. The fixed ASCII and non-ASCII results changed from Python `str` in standalone 2.7.3 to `unicode` in standalone and embedded 2.7.4. Accept `basestring` when both text types are valid, then normalize explicitly for the next text or byte boundary.
- Re-test Unicode validation and persistence assumptions. Jython 2.7.4 updated the fixed runtime data to Unicode 15.1 and resolved selected names that 2.7.3 did not; this is character-data coverage, not Python 3 text semantics.
- Preserve explicit codec and socket boundaries. The tested standalone runtimes and the Ignition embedding differed in default encoding behavior, so an embedded success does not prove a portable 2.7.4 conversion. Decode input bytes and encode output bytes with the protocol's stated codec.
- Separate an Ignition 8.3.8 API change from a Jython 2.7.4 change. A new `system.config` or `system.secrets` function name belongs to the Ignition surface and still needs exact scope, permission, resource, result, and side-effect evidence; it does not show that Python gained a feature.
- Treat an upstream release-note fix as a test hypothesis, not a project guarantee. Require a bounded positive and negative reproduction in the actual Java and Ignition scope before changing application logic, and keep environment-dependent or unreproduced items unproven.
- Build the migration test list from actual project boundaries: overloaded Java calls, Java text conversion, Unicode/name validation, raw socket or codec work, concurrency/callback ownership, serialization, and installed dependencies. Do not assign one universal upgrade-risk score; record the exact affected call, input, expected result, failure result, and cleanup for each case.

## Prove a dependency one level at a time

Do not collapse these evidence levels into a single claim:

1. **Name/discovery:** An inventory or path scan found a candidate name. This does not prove importability.
2. **Import:** A controlled import in the exact target scope returned a module. Import executes module initialization, so use only an approved fixed probe and do not call arbitrary imports read-only. Success does not prove the required members or behavior.
3. **Identity/capability:** Record the exact module or Java class, version when meaningful, loader/code source, and every required member. This does not prove the application operation.
4. **Focused behavior:** Exercise bounded positive and negative cases, exact input/output types, errors, limits, and cleanup in the target scope.
5. **Deployment/operation:** Prove packaging, configuration, permissions, ownership, restart/upgrade behavior, and every required Ignition scope before calling the defined integration supported.

The fixed `language-compat-v1` action contains import attempts for dataclasses, NumPy, and pandas because they are common unsupported assumptions, not because the API supplies them. All three raised `ImportError` on the tested Ignition 8.3.8 Gateway, including the last fully audited v0.42.0 regression. This proves only that those names were not importable through that tested loader at that time; it is not a permanent or universal impossibility claim.

Do not infer any package result from `language-compat-v1.passed`. In API v0.42.0 source, that Boolean covers only the fixed syntax and XML conditions; it does not include `environmentImports`. Read and report each exact `environmentImports.<name>.available` and `exceptionType` field with the API version, execution scope, and observation time. Treat a missing field, unexpected exception type, or stale result as unproven rather than converting the top-level pass into availability or absence.

The fixed `native-compat-v1` action separately found `.py` and `$py.class` import suffixes, zero binary-extension suffixes, and a Jython compiler warning that extension compilation is unsupported. Treat this as evidence against ordinary CPython wheel/C-extension installation on the tested baseline, not as proof about every optional bridge. NumPy or pandas becoming discoverable or importable later would still require levels 3–5 before use.

Unlike the language action's package observations, API v0.42.0 `native-compat-v1.passed` explicitly includes the fixed Jython implementation, `.py`/`$py.class` presence, zero C-extension suffixes, empty `.so`/`.pyd`/`.dll` suffix results, exact Jython compiler/warning behavior, the fixed pure-Python calculation/module-file shape, and the fixed Java calculation. A current pass can support only that combined baseline contract. It still does not prove an arbitrary package, wheel, native library, bridge, deployment, or application behavior; inspect the fields and `scopeNote`, and treat a schema mismatch as unproven.

## Apply the tested runtime baseline

- Target Jython `2.7.4`, not CPython and not Python 3.
- Do not use f-strings. They fail to compile with `SyntaxError` in this runtime.
- Do not use `async`/`await`, variable annotations, or function annotations. They fail to compile with `SyntaxError`.
- Remember that division of two integers uses Python 2 semantics: `5 / 2` evaluates to `2`.
- Make an operand explicitly floating point when a fractional result is required: `5.0 / 2` evaluates to `2.5`.
- Treat `str` and `unicode` as distinct types when handling text and encodings.
- Encode `unicode` before a byte-oriented boundary and decode received bytes explicitly. A non-ASCII UTF-8 round trip is verified; invalid UTF-8 raises `UnicodeDecodeError`.
- Jython 2.7.4 reports `unicodedata.unidata_version == "15.1.0"` in both the tested standalone and Ignition runtimes. The Unicode 15.1 names for U+2FFC and U+31EF resolve with `unicodedata.lookup` and Python 2 `\N{...}` escapes; the same cases fail on standalone 2.7.3. Treat this as updated character data, not as Python 3 language or API compatibility.
- For raw sockets, do not rely on Jython's implicit Unicode conversion. The same Jython 2.7.4 fixture used default ASCII in standalone and UTF-8 in the tested Ignition embedding, changing whether direct non-ASCII Unicode failed or sent bytes. Call `.encode("utf-8")` (or the protocol's specified encoding), set timeouts, cap reads/writes, and close sockets in `finally`.
- Keep raw `socket.send`/`sendall` findings separate from `system.net.httpClient`; one does not establish the other's behavior. For the tested HTTP client path, set its timeout, check `statusCode`/`good` and the required response data, and catch `java.io.IOException` explicitly for transport failures; the refused connection bypassed a Python-only `except Exception` handler.
- Do not emit Python 3 timing calls such as `time.monotonic()` or `time.perf_counter()` for this target. Both attributes were absent in the fixed standalone Jython 2.7.3, standalone Jython 2.7.4, and embedded Ignition Jython 2.7.4 matrix.
- For an elapsed-time deadline inside one running Gateway JVM, use `java.lang.System.nanoTime()` and compare differences only. The fixed calls returned `long` and were nondecreasing in all three runtimes. The origin is arbitrary: never persist a `nanoTime` value, present it as a timestamp, or compare it across JVM instances/restarts.
- Create one bounded deadline at operation entry and carry its remaining budget through every blocking call, retry attempt, delay, and completion wait. Do not restart the full timeout for each attempt. With non-negative integer milliseconds, the tested arithmetic was `deadline = now_nanos + timeout_ms * 1000000L` and `remaining_ms = max(0L, (deadline - now_nanos + 999999L) // 1000000L)`; sample `now_nanos` once per decision, cap every requested step to the remaining value, and stop at zero.
- Validate and bound timeout inputs before clock arithmetic. The fixed helper rejected a negative timeout and negative allocation with `ValueError` and a float timeout with `TypeError`. Treat that as this helper's integer-millisecond contract, not proof that every Ignition API rejects the same values. A supplied timeout also does not by itself prove cancellation, rollback, handler completion, or safe retry.
- Do not log an HTTP transport exception's full text or the request URL by default. The tested `IOException` text included the complete URL; log a stable operation label and error type, then re-raise or return a bounded sanitized error according to the caller contract.
- Use Java interop deliberately. Java classes are available to Jython, and returned Java objects may require Java methods or explicit conversion.
- Do not use an upstream Jython POM, upstream Gradle declaration, whole-product SBOM entry, installed filename, or embedded Maven metadata alone to claim which Java class/version a script will use. The published Jython 2.7.3 and 2.7.4 POM variants each declared zero dependencies, while their source Gradle files did declare libraries; the tested Ignition artifact also differed from upstream 2.7.4 for JFFI, Guava, and JLine metadata.
- Resolve the exact Java class in the actual Ignition scope and record a sanitized code-source filename when dependency identity matters. The fixed Gateway Web Dev probe resolved Jython from `jython-ia-2.7.4.0.jar`, but Commons Compress 1.27.1, Commons IO 2.18.0, Guava 32.0.1-jre, Bouncy Castle 1.78.1, ASM 9.9.1, and Netty 4.1.133.Final from separate Ignition jars. Those results are class- and scope-specific, not a general classpath guarantee.
- Treat unresolved fixed class probes as evidence of non-visibility through the tested loader, not proof that no related library code exists anywhere in the product. The fixed ICU4J `VersionInfo` and JLine `ConsoleReader` names were present in upstream/artifact inventory context but did not resolve through either tested Gateway loader.
- Do not trust `Package.getImplementationVersion()` as a universal dependency-version source. In the fixed probe, JFFI and JNR classes loaded from the Jython artifact reported the parent Jython manifest version `2.7.4`; combine code source with exact artifact metadata when a library version matters.
- Treat the Ignition SBOM as whole-product inventory, not active-runtime selection proof. The tested Ignition 8.3.8 SBOM listed both Jython 2.7.4rc1 and 2.7.3, while direct runtime and active-artifact evidence identified Jython 2.7.4 final.
- Expect Jython 2.7.4 to prefer a compatible fixed-arity Java method or constructor over a varargs alternative. The same compiled fixture selected varargs in 2.7.3 and fixed arity in standalone and embedded 2.7.4; keep a positive fixed-arity case and a varargs-only fallback in integration tests.
- Avoid APIs with multiple simultaneously compatible varargs overloads when a wrapper with one explicit signature is practical. Two fixed overlapping-varargs signatures selected different branches in 2.7.3 and 2.7.4; treat untested combinations as version-sensitive rather than relying on a general ordering rule.
- Do not assume every Java `List` supports Python slicing. Slicing the Java 17 immutable list returned by the tested `system.config` read raised `NoSuchMethodException`; use bounded iteration with `enumerate` and `break`, or explicitly copy to a Python list first.
- Pass Python functions to compatible Java single-abstract-method interfaces, including interfaces with default methods. Match the callback's required arity; a wrong-arity callback fails when invoked.
- Treat Java `char` results as text, not bytes. The fixed ASCII and non-ASCII locale characters were both `unicode`, not `str`, in standalone and embedded Jython 2.7.4; the same standalone fixture returned both as `str` in 2.7.3. Use `isinstance(value, basestring)` when either Python text type is valid.
- Expect Java methods returning a non-byte `char` to yield Python `unicode` in Jython 2.7.4. In the fixed headless `JPasswordField` test, its default U+2022 echo character and an explicitly set U+2022 value raised `IllegalArgumentException` when read in 2.7.3 but returned one-character `unicode` values in every tested 2.7.4 lane; an ASCII `*` read as `str` in 2.7.3 and `unicode` in 2.7.4. Keep Java-character handling text-oriented and test the exact component/API rather than replacing a valid non-ASCII default by assumption.
- Prefer explicit Java imports. In the fixed current comparison, `from java.util import *` exposed `ArrayList`, `Date`, `HashMap`, `Optional`, and `UUID` through the installed Ignition Jython assembly on Java 11 and Java 17, while direct launches of the stock standalone 2.7.3 and 2.7.4 JARs exposed none of those five names on either JVM; explicit `Date` import worked in every lane. Treat wildcard discovery as an embedding/package-manager fact, not a Jython-version guarantee. Java 21 remains untested here.
- Do not assume dataclasses, NumPy, or pandas are installed. The tested baseline Gateway returned `ImportError` for all three; discover the actual environment before choosing dependencies.
- Do not assume CPython binary wheels or C-extension packages work. The tested Gateway's default Jython import path advertised only `.py` and `$py.class`, and its Jython compiler refused extension compilation. Prefer Python 2.7-compatible pure-Python modules or Java/JVM libraries; identify and test any optional native compatibility bridge explicitly.
- Prefer explicit XML imports such as `from xml.etree import ElementTree` and `from xml.parsers import expat`. Wildcard XML import exposes `parsers` and `etree` here, but explicit dependencies are clearer.
- For interactive-input tooling, `codeop.compile_command` returned a code object for complete input, `None` for incomplete input, and raised `SyntaxError` for definitely invalid input in the tested runtime.
- When a compatibility boundary requires pickle, specify and document the protocol. Pure-Python pickle protocol 2 preserved the value and shared identity of the tested repeated Unicode reference; do not generalize that fixture to arbitrary object graphs.
