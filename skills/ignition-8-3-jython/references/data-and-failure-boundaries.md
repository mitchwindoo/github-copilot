## Handle data defensively

- Validate required keys, types, nulls, and quality before acting on values.
- Preserve qualified-value quality and timestamps when they affect the decision.
- Prefer protected Named Queries or prepared statements for database work. Current Ignition 8.3 documentation uses `system.db.execQuery` for a Named Query SELECT and `system.db.execUpdate` for a Named Query change; both were present in the tested Gateway. The older `runNamedQuery` name was also present, but do not reach for an older signature unless the existing project contract or current function documentation confirms it. Bind values as parameters; never concatenate caller data into SQL, and do not treat value placeholders as a way to parameterize table names, column names, or SQL syntax.
- For an explicit database transaction, validate inputs, callback/resource availability, and a bounded work list before calling `beginTransaction`. Treat ownership as acquired only after begin returns a valid transaction ID; if begin raises before returning an ID, do not invent an ID or call rollback/close with `None`.
- After ownership is acquired, commit only after every required operation and application-specific result-count check succeeds. On a work or count failure before commit, attempt rollback and then always attempt close. Preserve the work failure as primary while reporting rollback/close failures separately with bounded, sanitized diagnostics.
- Treat a commit-call failure as an outcome-unknown boundary. A rollback attempt and close attempt may still be required for cleanup, but do not claim the unit rolled back, do not report success, and do not retry automatically: a real database may have applied the commit before the caller observed the failure. Require an application-specific idempotency, deduplication, readback, or reconciliation contract before recovery.
- If commit returns successfully but close fails, report that the work may already be committed and cleanup failed; do not rerun the transaction as if nothing happened. The fixed adapter labels this `committed_close_failed` and keeps retry unsafe.
- Put rollback/close ownership cleanup in `finally` so fixed Python control-flow and Java-error cases propagate only after cleanup is attempted. Catch only the expected Python/Java operational families for bounded transaction results; do not swallow `SystemExit`, `KeyboardInterrupt`, `GeneratorExit`, or Java errors as ordinary database failures.
- Close every acquired transaction after commit or rollback. Ignition documents that an open transaction consumes a pooled connection, its inactivity timeout resets each time it is used/committed/rolled back, and a timed-out transaction is automatically closed and its ID invalidated. Treat that timeout as an idle-connection guard, not as a total operation deadline; apply a separate bounded elapsed-time budget where the workflow needs one.
- Verify update counts against the actual statement contract and document database, isolation, timeout, scope, and driver assumptions. The fixed lifecycle matrix required count `1`, at most eight steps, and a bounded text ID only as test-contract values; do not copy those limits into unrelated database work.
- Treat tag reads as `QualifiedValue` results and tag writes as per-path `QualityCode` results. Validate the exact result count before pairing by index, preserve one stable status per requested item, and check every quality before using a read or claiming a write succeeded; a returned list is not itself proof that every path was good.
- Do not use `QualityCode.isGood()` alone as final write confirmation. In standalone Jython 2.7.3, standalone 2.7.4, and embedded Ignition 8.3.8 Jython 2.7.4, `QualityCode.Good_WritePending.isGood()` returned `True` and its code was `2`; Ignition documents that state as a write still in progress. Classify it as pending until a later documented final result or independent readback establishes completion.
- A readback value that equals the requested value does not override a bad or pending write result; the value may have existed before the attempt or may be stale. For each item, require a final acceptable write result first, then a valid `QualifiedValue`, an acceptable non-pending read quality, and expected-value equality. Define which other good subcodes are acceptable for the specific domain instead of treating every good-quality code as equivalent.
- Treat any invalid object, result-count mismatch, bad quality, pending state, or value mismatch as an explicit per-item failure. Overall success requires every requested item to be verified. Return bounded stable diagnostics such as item index and status; do not expose raw exception text or silently drop failed items.
- Do not automatically retry an unknown, pending, partially completed, or non-idempotent write. Retry only when the operation contract states how duplicate delivery is prevented or made harmless, the caller can identify the same logical operation, and the remaining shared deadline permits another attempt. Otherwise return the partial/pending state for reconciliation.
- Ignition 8.3 automatically exposes datasets through PyDataset-style iteration. The fixed Gateway fixture created a `BasicDataset` with current `system.dataset.toDataset(headers, rows)` and iterated `PyDataset$PyRow` values with field and index access while preserving `None`. Use the exact current `toDataset` capitalization for new code; do not emit deprecated `toPyDataSet` or older `toDataSet` merely because both legacy names remain available on this Gateway.
- Validate JSON after decoding: require the expected top-level type, required keys, value types, null policy, and size limits. In the fixed 8.3.8 fixture, `system.util.jsonEncode` returned `unicode`, valid `jsonDecode` returned a matching `dict`, and malformed JSON raised Java `org.json.JSONException`; catch that Java type explicitly when malformed input is an expected failure. Do not assume Ignition's decoder follows Python `json.loads`, whose fixed standalone malformed-input case raised Python `ValueError`.
- Carry instants across integration boundaries as documented epoch milliseconds when practical. Name the field so its unit is explicit, such as `eventTimeMillis`, and validate the exact boundary contract before conversion. If the contract requires an integer, use `type(value) in (int, long)` rather than `isinstance(value, (int, long))` when Boolean values must be rejected; reject floats instead of silently rounding. The fixed matrix showed that `1700000000` interpreted as milliseconds produces the plausible but wrong `1970-01-20T16:13:20.000Z`, while `1700000000000` produces `2023-11-14T22:13:20.000Z`.
- Treat `java.util.Date` as an instant, not as a complete local date/time presentation contract. Current Ignition 8.3 `system.date.fromMillis` and `toMillis` document milliseconds from the Unix epoch in UTC. The fixed Gateway round trip returned `java.util.Date` and `0`; `system.date.getTimezone()` returned non-empty `unicode`, but its documented result depends on execution scope. Do not let an implicit Gateway, client, Perspective, JVM, or host default choose business meaning unnoticed.
- Make the format, locale, and region time-zone ID explicit when parsing or displaying a fixed-zone business value. Current `system.date.format` exposes only the date and format arguments, and `system.date.parse` exposes date text plus optional format and locale, so neither function supplies an explicit time-zone argument. When the requirement cannot use the execution scope's documented default, use a separately verified adapter; the fixed Jython adapter created a new `java.text.SimpleDateFormat` with `Locale.US`, set `lenient` false, and set `java.util.TimeZone` explicitly for each operation.
- Validate a time-zone ID against `TimeZone.getAvailableIDs()` before calling `TimeZone.getTimeZone(id)`. In the fixed Java 17 matrix, the unknown ID `Not/A_Real_Zone` silently resolved to `GMT`; a returned `TimeZone` object therefore did not prove that caller input was valid. The fixed `America/Chicago` and `UTC` results do not establish every zone or future time-zone-database rule.
- Require strict parsing and complete input consumption. The fixed `SimpleDateFormat`/`ParsePosition` adapter accepted `2024-01-02T03:04:05.006Z` and rejected February 30, trailing text, and the nonexistent `America/Chicago` wall time `2024-03-10 02:30:00`. Do not treat a non-null partial or lenient parse as validation.
- Preserve an offset or epoch value when a local wall time can be ambiguous. The fixed fall-back case produced two distinct instants for `2024-11-03 01:30:00` in `America/Chicago`, one at `-0500 CDT` and one at `-0600 CST`; wall-clock text alone could not identify the instant.
- Distinguish elapsed duration from calendar arithmetic. Across the fixed spring transition, 24 elapsed hours after `2024-03-09 12:00:00 -0600` was `13:00:00 -0500`, while adding one calendar date produced `12:00:00 -0500`. State whether the requirement is an elapsed interval or the next local calendar day before choosing arithmetic.
- Convert Java collections intentionally and keep returned structures bounded. Avoid JSON field names that differ only by letter case when case-insensitive consumers may parse the response.
- Keep credentials, API keys, private endpoints, and customer identifiers out of code and logs.
- Catch the narrowest expected Python and Java exception types. In the fixed three-runtime matrix, Python `ValueError` was caught by Python `Exception`; `SystemExit`, `KeyboardInterrupt`, and `GeneratorExit` bypassed `Exception` and belonged to Python `BaseException`; and the selected Java throwables belonged to neither Python base. Import and catch a documented Java type explicitly instead of assuming Python `Exception` or `BaseException` covers it.
- Do not use bare `except:`, Python `BaseException`, or Java `Throwable` as routine recovery handlers. The fixed bare handler caught all eight Python/Java cases, while Java `Throwable` included the selected Java assertion error. Catching a termination/control-flow exception or Java error does not make it recoverable. Propagate it unless a narrowly documented boundary explicitly owns that condition.
- A tuple containing fixed explicit Python and Java types caught both `ValueError` and `java.io.IOException`, but keep separate handlers when cleanup, retry, status, or sanitization differs. Do not broaden the tuple to base types merely to make unlike failures look uniform.
- Put unconditional cleanup in `finally`. The fixed `finally` block ran for all eight routed cases, including Python termination/control-flow exceptions and the selected Java error. Cleanup does not authorize swallowing the active failure; preserve it unless the caller contract explicitly defines a handled result.
- Validate cleanup targets and preconditions before starting the protected operation, and keep `finally` cleanup minimal. In all four fixed combinations, a Python or Java exception raised during `finally` replaced the active Python or Java operation exception. If cleanup itself can fail, guard it separately and follow an explicit caller contract that preserves the original operation failure as primary while reporting only bounded, sanitized cleanup diagnostics. Do not let cleanup failure silently replace the original.
- A manually raised `InterruptedException` remains routing evidence only; do not use it to simulate cancellation. The separate fixed real-thread matrix established only its exact Java 17/Jython 2.7.3/Jython 2.7.4 and embedded `invokeAsynchronous` cases: interruptible latch waits observed interruption, the workers restored the flag after bounded cleanup, and every owned thread/executor terminated. It does not establish interruption behavior for arbitrary Ignition calls, drivers, sockets, or third-party libraries. Likewise, the selected Java assertion-error route does not establish that Java errors should be caught. Sanitize operational messages and either propagate the expected failure or return a documented bounded result.
