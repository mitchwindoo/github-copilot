# Ignition 8.3 Perspective

Skill version: `1.74.0`

Use this skill only for Ignition 8.3 Perspective work. Treat Ignition 8.1 examples, exports, resource shapes, runner behavior, and API behavior as unverified inputs until they are reproduced on the target Ignition 8.3 build.

Treat this as an API-enabled skill. Obtain the Gateway base URL, API credential, target project, and any requested resource namespace at runtime.

## Safety boundary

- Discover the live Gateway version, project, resources, and callable API operations before acting.
- Use only the user-approved target project. Do not create, rename, copy, or delete a project unless explicitly requested.
- Put new resources beneath a dedicated, caller-approved namespace that does not collide with existing work.
- Preserve created views, routes, tags, UDTs, and scripts. Do not delete or clean them up unless explicitly requested.
- Keep credentials and private connection values out of generated resources and reusable documentation.
- Require a bounded write plan, current-state preconditions, exact readback, and API-observable runtime validation for every mutation.
- For every authoring and runtime test, always query and save the bounded official Gateway log window, even when no problem is expected and the page appears correct. Classify every returned WARN-or-higher entry; never infer clean execution from paint, HTTP success, or browser-console silence.
- Before every client interaction run, require an active trial or license and attach browser console, page-error, and request-failure listeners before navigation. If any Gateway-scoped action reports no Gateway connection, reject all subsequent evidence from that browser session, re-check license/trial state, and repeat from fresh sessions; Gateway logs alone may remain clean for this failure mode.
- Use an official Ignition OpenAPI operation first. Use the documented `llmImport` Web Dev API only when OpenAPI lacks the required capability.
- Do not assume `llmImport` exists. It exposes one optional project-scoped JSON-dispatch POST route, not platform endpoints. Read its health route, record its version, and require the intended action in `availableActions`; if it is absent or incompatible, its POST route and every dispatched action are unavailable. Omit those calls and continue with the platform-provided Ignition OpenAPI capabilities exposed by `/openapi.json`, subject to installed modules, authentication, and permissions.
- Decode and encode every project JSON resource explicitly as UTF-8. For non-ASCII text, add an independent exact-string or code-point assertion and inspect the rendered DOM/screenshot; never trust a comparison when both sides passed through the same decoder.
- When neither interface supports the operation, add the smallest generally useful `llmImport` action with authorization, input validation, structured errors, readback, positive and negative tests, contract versioning, and regression coverage.
- Do not use browser, Designer, or other computer-use automation for authoring. When the caller approves client validation, use programmatic browser control only for rendering, screenshots, geometry, console inspection, and bounded interaction tests.
- Do not infer a Perspective JSON or project-resource schema from documentation, Ignition 8.1 material, or one nearby component type.

## Workflow

1. Confirm the exact Ignition 8.3 Gateway build and Perspective module state.
2. Discover the live OpenAPI document and, when needed, the documented `llmImport` action surface.
3. Inspect the approved target project and its Perspective resources without changing them.
4. Select one additive resource change beneath the approved namespace.
5. Export the current project, declare the exact expected delta, and define positive, negative, readback, runtime, and log checks.
6. Immediately before import, export again and abort if any base resource drifted.
7. Apply the narrowest supported API operation, wait for activation, and export or query the result for exact readback.
8. Exercise every available API-observable runtime check. Always save and inspect bounded official Gateway WARN-or-higher logs, including after delayed cleanup and every tested lifecycle edge such as open, navigation, reload, close, or official session termination. A clean screen or earlier clean interval is not a substitute for the post-action log query. For a caller-approved client test, capture painted screenshots, element geometry, exact URLs, console diagnostics, and bounded interactions; correlate them with official session reads and the saved Gateway logs.
9. Stop on schema uncertainty, authorization failure, drift, partial writes, unexpected changes, runtime errors, or missing evidence.
