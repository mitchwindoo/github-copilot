# Parameter and Coercion Guardrails

## Parameters

- Require every declared Named Query parameter before Designer preview, target script runs, or Perspective bindings. Also require every declared parameter in Perspective query bindings; do not omit a required binding parameter to mean empty, all rows, or default behavior. Map those states to an explicit sentinel or nullable value that is still passed under the declared parameter name, then branch intentionally in SQL. Target runtime can be more permissive than validation: on a tested Query-type Value-param target, a missing declared key reached SQL as `NULL` and an extra map key was ignored. Do not treat a quiet target result as proof that the parameter map is correct.
- Reject unexpected parameter names before runtime to catch typos, and pass exactly one params dictionary/Map. Use explicit `None` or an allowlisted sentinel for intentional null/default/all behavior instead of relying on omitted-key behavior from one target.
- Treat Named Query `Value` parameter coercion as target-specific. Parameter metadata does not guarantee that JSON, Perspective, or Jython numbers, booleans, and timestamps bind as database-native numeric/boolean/timestamp values. UI, URL, and Perspective values often arrive as strings; validate and normalize before passing where practical, or cast/parse deliberately in SQL with explicit companion fields such as `value_parse_state`, `value_is_null`, `row_count`, or `invalid_reason` when invalid, zero, false, empty, and null states matter. Ask the user to verify native numbers, numeric strings, false/zero, invalid text, and explicit nulls on their target database. Do not assume invalid numeric/date text fails automatically: some targets or functions can coerce invalid numeric text to zero or invalid date text to `NULL`.
- Treat raw query parameter values and Perspective query-binding parameter expressions differently. Perspective binding `config.parameters` entries are expression/property-reference strings. For a literal string constant, JSON-encode an Ignition expression string literal such as `"\"<literalValue>\""`. Passing a raw wildcard string directly in a Perspective binding can be parsed as an expression and render a component error. For dynamic values, use property references such as `"{view.params.asset}"`, `"{view.params.matchText}"`, `"{../Input.props.text}"`, or `"{../FilterDropdown.props.value}"`.
- For Checkbox filters, bind boolean state from `"{../FilterCheckbox.props.selected}"`, add a visible selected-state echo plus a query-derived row-count/status label, and ask the user to verify checked, unchecked, and rechecked states in the browser. Treat the bound value as target-coerced data, not guaranteed database-native boolean: branch deliberately for native true/false, string `true`/`false`, numeric-looking `1`/`0`, explicit null, missing params, unexpected params, and invalid text when the SQL distinguishes those states.
- For Toggle Switch filters, bind boolean state from the component's `props.selected`, for example `"{../FilterToggle.props.selected}"`, not from a guessed `props.value`. The official Perspective Toggle Switch docs describe `props.selected` as the selected on/off state and the component as similar to Checkbox. Add a visible selected-state echo plus a query-derived row-count/status label, and ask the user to verify selected, unselected, and reselected states in the browser. Treat the bound value as target-coerced data, not guaranteed database-native boolean: branch deliberately for native true/false, string `true`/`false`, numeric-looking `1`/`0`, explicit null/default, missing params, unexpected params, and invalid text when the SQL distinguishes those states.
- For Numeric Entry Field filters, bind numeric input from `"{../MinValue.props.value}"` or the actual sibling component name, add a visible numeric-value echo plus a query-derived row-count/status label, and ask the user to verify the initial value plus at least two edited values such as a decimal threshold and zero/all-state threshold in the browser. The official Perspective Numeric Entry Field docs define `props.value` as a number or numeric string and support `direct`, `protected`, and `button` edit modes, so choose the edit mode intentionally and have the user prove it on the target. Treat the bound value as target-coerced data, not guaranteed database-native numeric: branch deliberately for native numbers, numeric strings, decimals, zero, explicit null/empty, missing params, unexpected params, and invalid text when the SQL distinguishes those states. Design parse/status/display companions such as `param_state`, `param_text`, `threshold_value`, `threshold_display`, and `row_count` when the UI must distinguish invalid, null/default, zero, and filtered states.
- For Slider filters, bind downstream query params from the component's `props.value`, add a visible slider-value echo plus a query-derived row-count/status label, and ask the user to verify the initial value, an actual track/handle change, an off-step/manual or bound value when step matters, a zero/all or low-threshold value, and a max/no-row state if that state matters. The official Perspective Slider docs expose `value`, `min`, `max`, `step`, and `labels`, and note that `step` does not force manually or binding-set values into that step size; treat `min`, `max`, and `step` as UI constraints, not complete validation. Ask for target-side proof of native-number, numeric-string, off-step decimal, min/max/zero, null/empty/default, invalid, missing, and unexpected branch behavior when the SQL distinguishes those states. Design explicit clamp/parse/status companions when the UI must distinguish out-of-range, invalid, all-state, and no-row states.
- For Radio Group filters, define explicit `props.radios[].value` entries, bind the downstream Named Query parameter from the component's `props.value`, add a visible selected-value echo plus a query-derived row-count/status label, and ask the user to verify the initial option plus at least two option changes in the browser. The official Perspective Radio Group docs define `props.value` as the selected radio value and allow string, integer, boolean, or null values; treat that value as target-coerced data and branch deliberately for allowlisted values, case/normalization choices, explicit all-state sentinels such as `__ALL__`, null/empty/default, missing params, unexpected params, and invalid text when the SQL distinguishes those states.
- For DateTime Input filters, bind the downstream Named Query parameter from the component's `props.value`, add a visible DateTime value echo plus a query-derived row-count/status label, and ask the user to verify initial/in-range, alternate in-range, future/no-row, and clear/null states in the browser. The official Perspective DateTime Input docs define `props.value` as a Date object or timestamp in milliseconds and expose display/input properties such as `formattedValue`, `pickerType`, `minDate`, `maxDate`, `format`, `locale`, and `dismissOnSelect`; treat the bound value as target-coerced data, not guaranteed database-native timestamp. Ask the user to verify or design branches for epoch-millis, ISO/date text, explicit null, empty/default, future/no-row, invalid text, missing params, and unexpected params when the SQL distinguishes those states. Preserve target-exported Named Query resource metadata when adapting existing date queries, and ask the user to prove DateTime/Timestamp parameter metadata on their target before relying on it.
- Treat a syntactically present Perspective property-reference string as structure, not proof that the target component/property exists. A missing sibling component or missing property can feed SQL `NULL`, hit a default/all-rows branch, or surface as a binding error. When a nullable/default/all branch could hide a typo, ask the user to inspect the Perspective binding JSON for the exact component/property path and verify in the browser with visible value/state/row-count echoes for both the intended reference and a known missing-reference control or screenshot/error state.
- Use raw Jython `system.db.runQuery` only for trusted fixed `SELECT` text with no user, URL, Perspective property, tag, or variable values. It is a standard-statement helper, not a prepared-parameter helper: do not use `?` placeholders or pass parameter lists/dictionaries to `runQuery`. Use Named Query `Value` params or `system.db.runPrepQuery` when values must be supplied dynamically. `runQuery(sql, <databaseConnection>[, tx])` returns a PyDataSet rowset; check row/column counts before indexing and expect empty results to preserve column metadata. In reusable Gateway/Perspective helpers, prefer passing the database connection explicitly unless the user confirms the target default database dependency. Ask the user to verify the result shape, empty result, transaction shape, and default-database assumptions on their Gateway before treating existing raw `runQuery` code as portable.
- Use raw Jython `system.db.runUpdateQuery` only for trusted fixed `INSERT`/`UPDATE`/`DELETE` text with no user, URL, Perspective property, tag, or variable values. It is a standard-statement write helper, not a prepared-parameter helper: do not use `?` placeholders or pass parameter lists/dictionaries to `runUpdateQuery`. Prefer Named Query `Value` params or `system.db.runPrepUpdate` when values must be supplied dynamically. By default, `runUpdateQuery(sql, <databaseConnection>[, tx])` returns affected-row count; ask the user to verify expected counts such as `1` for a single-row insert/update/delete and `0` for a legitimate no-match update/delete. Use `getKey=1` only when the target database, driver, table definition, and statement support generated-key retrieval, then ask the user to verify the returned key with follow-up readback. Keep `skipAudit=True` explicit and rare. For target-side write probes or migrations, ask the user to pass the database explicitly, keep `tx` separate, rollback during tests, and verify post-rollback or cleanup state because DDL lifecycle and generated-key behavior are driver-specific.
- Treat `UpdateQuery` Named Queries as writes/action calls, not read previews. Use Designer or target-side metadata only to inspect the query and parameters; execute the write only from intentional script code or a controlled Gateway/Perspective workflow. Call `system.db.runNamedQuery(<projectName>, <namedQueryPath>, params)` for the write, ask the user to verify the returned affected-row count, and verify durable readback or rollback state on the target. Use keyword `getKey=1` only when generated keys matter and the target database/table/query support it, then verify the returned key with a follow-up read. Keep params as one dictionary/Map, not a list, and pass every declared param explicitly; if a nullable omitted param appears to work on one target, still prefer an explicit `None` or sentinel value and ask the user to verify behavior.
- For TextField-driven filters, inspect or set `props.deferUpdates` intentionally. With `deferUpdates: true`, typed text can be visible while bound consumers still use the previous committed value until Enter or blur. With `deferUpdates: false`, the bound echo/table should refresh from the typed value without Enter or blur. Ask the user to verify the chosen behavior in the browser.
- For TextField/search filters that feed SQL `LIKE`, decide whether typed `%` and `_` are intended wildcards or literal characters before binding. Named Query `Value` params prevent SQL injection, but they do not make `LIKE` metacharacters literal. Leave a raw TextField value such as `:matchText` only for deliberate wildcard mode. For literal search, build an escaped companion value in trusted code before binding, for example `!` -> `!!`, `%` -> `!%`, and `_` -> `!_`, then use SQL such as `displaypath LIKE :escapedText ESCAPE '!'`; adding `ESCAPE '!'` alone does not stop unescaped `%` or `_` from acting as wildcards. Ask the user to verify both a wildcard case and a literal escaped case in Designer/browser, with a visible input echo, row count, and row list/table so wildcard-confuser rows cannot hide.
- For Text Area filters, bind multiline text from the component's `props.text`, for example `"{../FilterTextArea.props.text}"`, not from a guessed `props.value`. The official Perspective Text Area docs describe it as multiline text display/editing and define `text` as a string, `deferUpdates` as deferring `props.text` updates until focus is lost or Enter is pressed, and `wrap` as the line-wrapping control. Add a visible text echo that normalizes line breaks for display, such as replacing newline with `<LF>`, plus a query-derived row-count/status label. If `props.deferUpdates` is true, ask the user to verify a focused uncommitted edit separately from the committed blur/Enter state; for multiline entry, prefer a real keyboard edit plus Tab/blur commit proof because synthetic DOM fills or screenshots of the control alone may not prove bound `props.text` changed. Ask the user to verify multiline text, single-line text, empty/default, null/default, no-match or partial text, SQL-looking text, missing-param behavior, and unexpected-param behavior in Designer/browser or controlled target-side checks when those states matter. Treat newline content as data passed through a Named Query `Value` parameter; do not concatenate it into SQL or switch to a QueryString parameter for user-entered text.
- For enum/select filters, use explicit Dropdown option `value` entries that are valid SQL parameter values, bind the Named Query param from `props.value`, and verify at least one matching option plus one no-match or alternate option.
- If Dropdown options come from a query binding, return stable `label` and `value` columns from the options Named Query or add a script transform that converts Dataset/PyDataSet or row-list results into option objects like `{"label": str(label), "value": str(option_value)}`.
- Treat `ScalarQuery` Named Queries as scalar contracts, not rowset contracts. `system.db.runNamedQuery(<projectName>, <namedQueryPath>, params)` returns the first column of the first row as a plain scalar for `ScalarQuery`; later columns and later rows are outside the contract. Both a first-column SQL `NULL` and zero returned rows can surface as a `None`-like or blank result, so use a Query-type rowset with explicit companion columns such as `row_count`, `value_is_null`, or a sentinel value when the UI or script must distinguish empty from null. Pass one params dictionary/Map, not a list. If a declared value may be empty or optional, pass an explicit `None` or sentinel and branch intentionally instead of relying on omitted-parameter behavior from one target. Ask the user to confirm the target query type/export and scalar return shape before using it in a Perspective label, KPI, or helper script.
- In script transforms or Project Library helpers that consume Query-type Named Query results or prepared-query reads, treat results as Dataset/PyDataSet-like values. Use `getRowCount()`/`getColumnCount()` before row access and `getValueAt(row, columnIndex)` for direct single-value reads; use name-based access only when the returned object supports it. Normalize with `system.dataset.toPyDataSet(value)` before iterating rows or using `row["<columnName>"]`, then convert rows to plain dictionaries or option objects before returning data for Perspective table/options helpers. Empty results can still preserve column metadata while `len(system.dataset.toPyDataSet(value))` is `0`, so never index row 0 until the row count is positive. Do not use truthiness to decide whether a query value exists: `None`, `""`, `0`, `0.0`, and false-like numeric zero can all be falsey in Jython while meaning different SQL/UI states. Use explicit `value is None`, string length checks, numeric comparisons, and row-count guards. Require returned column names to be unique and simple before converting to dictionaries, option objects, or Perspective table fields. Duplicate names are unsafe: index access can still expose separate physical columns, while name access or dictionaries may collapse or overwrite one value. Avoid spaces, hyphens/punctuation, and reserved words for fields consumed by tables or transforms; ask the user to rename SQL aliases, preferably to unique `snake_case`, in the target query.
- Use `system.db.runScalarQuery` or `system.db.runScalarPrepQuery` only when the intended contract is exactly one first-row/first-column value, such as `COUNT(*)`, `MAX(...)`, or a status value. Scalar calls return a plain scalar, not a Dataset/PyDataSet; later columns and later rows are discarded. Treat `None` carefully: it can represent a SQL `NULL` in the first row/column or no returned rows at all. If the difference between zero rows and SQL NULL matters, ask the user to verify a rowset query with row-count checks or return explicit companion columns such as `row_count` and `value_is_null`. `runScalarPrepQuery` still uses the same ordered list/tuple parameter rules as other prepared calls.
- For multi-select Dropdowns, set `props.multiSelect: true` and treat `props.value` as an ordered list of selected option values. Do not pass that list into one SQL/Named Query parameter as a pretend dynamic `IN` list; for a bounded small multi-select filter, declare scalar parameters per slot and bind them with indexed property references such as `"{../FilterDropdown.props.value[0]}"` and `"{../FilterDropdown.props.value[1]}"`.
- For optional "all rows" filters, prefer an explicit allowlisted sentinel value such as `__ALL__` over omitting the parameter; keep the Named Query parameter required and branch in SQL with a bounded predicate such as `:matchText = '__ALL__' OR displaypath LIKE :matchText`.
- If the UI needs a user clear button, use the documented Dropdown `props.showClearIcon: true` property rather than an invented `clearable` prop, and define `props.placeholder` as an object such as `{"text": "Choose a filter"}`.
- For date/time filters, do not assume URL/query-string strings, route params, DatePicker values, Perspective DateTime Input `props.value`, epoch millis, and Named Query DateTime/Timestamp params coerce the same way. When the source is `page.props.urlParams`, the conservative design is to bind values into required Value/string Named Query params and normalize or cast in target SQL, such as `datetime(:startTime)`, `CAST(:startTime AS TIMESTAMP)`, `to_timestamp(:startTime, ...)`, or the target database's timezone-aware equivalent, unless the user's target export or target-side proof shows DateTime/Timestamp params work. When the source is a DateTime Input component, bind `props.value` into a required Value param and normalize epoch-millis/text/null/invalid states in SQL unless the target proves DateTime/Timestamp metadata works. Ask the user to verify broad/in-range, future/no-row, inverted/invalid, omitted/null/empty states in Designer, the browser page, or their database client, and to treat unparseable date text as a first-class state because some target functions return `NULL` instead of throwing. Do not assume returned SQL date/time expressions arrive in Ignition as Java Date values: target databases and drivers can return date/time function outputs as text, epoch companions as integer-like values, Julian-style values as floats, and invalid/empty/null inputs as null companions. Ask the user to verify returned timestamp cell types and timezone normalization on the target. Design explicit companion columns such as `iso_timestamp`, `epoch_millis`, `parse_state`, and `source_timezone` or normalization-state fields; parse and format intentionally before Jython date math or UI display, and call out index/performance effects for target review.
- For dynamic `IN` filters, do not pass an array, CSV string, or selected-value list into one Named Query `Value` param and expect it to expand. A predicate such as `displaypath IN (:matchCsv)` treats `matchCsv` as one scalar value; `<valueA>,<valueB>` is not the same as two placeholders and should return no exact match unless the database row literally contains that comma-separated string. Prefer a bounded placeholder shape such as `displaypath IN (:match0, :match1)` with one declared Value param per slot, or generate the placeholder list in trusted code from a validated value count. Handle empty lists before SQL, keep every declared slot present in Perspective bindings, and ask the user to verify exact-match, mixed match/no-match, all-no-match, empty, and null-slot states.
- For raw Jython `system.db.runPrepQuery`/`runScalarPrepQuery`/`runPrepUpdate`, pass params as ordered lists/tuples with one intentional value per `?` placeholder; use `[None]` for a SQL NULL placeholder instead of omitting that slot. Never pass scalar strings, numbers, dictionaries, or a list of parameter dictionaries. Validate placeholder counts before calling. Ask the user to verify target driver behavior if existing code omits params: SQLite evidence showed missing params via `[]` or `None` can become SQL NULL while extra params and scalar/dict params failed, but other drivers may reject or bind differently.
- Do not pass secrets as query params.
- Validate enum-like params before they reach SQL.
- Treat Database `<Parameter>` Named Queries as target-specific. Do not claim dynamic database selection works from export shape alone; ask the user to verify each approved target connection in Designer or the target client because some targets may still look for a literal `"<Parameter>"` connection at runtime.
