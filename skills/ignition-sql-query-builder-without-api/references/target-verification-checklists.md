# Target-Side Verification Checklists

## Target-Side Verification Checklist

When the LLM cannot reach the Gateway, give the user checks like these instead of claiming success:

- In Designer, confirm the Named Query path, database connection, parameter names/types, enabled state, and max-return settings.
- If a Named Query was copied or adapted from an export, confirm Designer can load it and that a Designer preview or controlled `system.db.runNamedQuery` call executes it. File/export visibility alone is not enough proof that the project runtime loaded the resource correctly.
- Run the Named Query preview in Designer with match, no-match, empty/null, and hostile-looking text values that match the intended UI flow.
- Open the Perspective page in a browser and confirm visible title/content, visible filter echo, row-count/status label, expected row presence/absence, empty-state label, and relevant console errors.
- Verify SQL `NULL`, empty string, single-space/blank, numeric zero, and false-like values with visible markers or companion fields when the distinction matters; inspect transforms for `is None`, string length checks, numeric comparisons, and row-count guards instead of truthiness checks.
- For query-string filters, verify `window.location.search`, `window.location.hash` when `#` may appear, decoded visible echoes, and the dependent table/label result.
- For route params, verify both encoded and raw delimiter cases that matter to the design.
- For Checkbox/Toggle Switch/Dropdown/TextField/Text Area/Numeric Entry/Slider/DateTime Input filters, verify the selected/typed/checked/multiline/numeric/slider/date-time value, the visible echo, and the query-backed label/table update together. For Checkbox filters, verify checked, unchecked, and rechecked states plus true/false/null/invalid branch behavior when the SQL distinguishes those states. For Toggle Switch filters, verify selected, unselected, and reselected states from `props.selected`, and verify true/false, string/numeric-looking boolean, null/default, invalid, missing, and unexpected behavior when the SQL distinguishes those states. For Text Area filters, verify a multiline value, a single-line value, an empty/default branch, and the committed-vs-uncommitted behavior when `deferUpdates` is true; ask the user to verify newline handling, null/default, no-match, SQL-looking text, missing, and unexpected parameter behavior when those states matter. For Numeric Entry Field filters, verify the initial value, an edited decimal or alternate threshold, and a zero/all-state or low-threshold value; ask the user to verify null/empty/default, invalid, missing, and unexpected parameter behavior in Designer or controlled target-side checks when those states matter. For Slider filters, verify initial, track/handle changed, off-step/manual or bound, zero/all or low-threshold, and max/no-row browser states when they matter; ask the user to verify number/string, off-step decimal, min/max/zero, null/empty/default, invalid, missing, and unexpected parameter behavior in Designer or controlled target-side checks. For DateTime Input filters, verify initial/in-range, alternate in-range, future/no-row, and clear/null browser states; ask the user to verify epoch-millis, ISO/date text, null/empty/default, invalid, missing, and unexpected parameter behavior in Designer or controlled target-side checks when those states matter.
- For Table-selection detail pages, verify the unselected initial state and then click at least two different master rows. Confirm the selected-key echo, hidden helper key availability, detail row count/status, and detail row values all change together. Ask the user to verify valid key, second valid key, explicit null/no-selection, invalid text, SQL-looking text, missing required params, and unexpected params in Designer, the browser, or controlled target-side checks. Inspect the view JSON or Designer binding panel to confirm the detail binding path references `props.selection.data[0].<stableKeyColumn>` and that `props.columns` includes the hidden helper field with `visible: false`.
- For polling, verify a visible timestamp/tick or changing status label changes without reload.
- For manual refresh buttons, verify the exact bound component/property, the `refreshBinding("<boundPropPath>")` call target, disabled polling when proving manual-only refresh, a visible query value stable before the click, and a changed query value plus click/status echo after the click. For IA Tables, refresh `props.data` on the Table and verify from data-derived row count/tick/status or row values, not only the table's paged/virtualized DOM.
- For paged IA Tables, verify a row-count label, first-page row, off-page row absence before paging, pager control, and off-page row presence after paging.
