# Verification and diagnostics

## Evidence ladder

For each mutation, collect:

1. Local JSON/schema and scope validation.
2. HTTP status, response headers allowlist, and raw body.
3. Semantic operation counts and per-item diagnostics.
4. Exact configuration export and normalized diff.
5. Runtime member/parameter/alarm reads with value type, quality, and timestamp.
6. Mandatory bounded Gateway logs for every new or changed UDT test; add audit rows when available.
7. Restart or lifecycle proof only when explicitly authorized in a disposable lab.

## Known quality outcomes

Examples observed on the verified 8.3.8 target:

| Quality | Typical tested cause |
|---|---|
| `Good` | Valid memory value, parameter, expression, static Reference, alarm runtime property |
| `Bad_NotFound` | Missing tag/member after partial replacement or invalid path |
| `Bad_Unsupported` | Reading a folder as a value |
| `Uncertain_InitialValue` | Unresolved parameterized Reference source path |
| `Error_Config` | Invalid configured expression syntax |
| `Error_ExpressionEval` | Missing/literal nested parameter or null numeric evaluation |
| `Error_TypeConversion` | Literal `"null"` in numeric evaluation |

Do not collapse these to a Boolean. Preserve exact names/codes and diagnostic messages exposed by the target.

## Mandatory bounded log check

For every new or changed UDT runtime test:

Use the consolidated `llm-tools` project for the test when it provides the required guarded operations. A new project is not a default isolation mechanism; create one only when `llm-tools` cannot safely or faithfully exercise the capability, and preserve the reason in the evidence.

1. Record an epoch-millisecond or UTC start immediately before the first import.
2. Create the UDT and exercise the intended runtime transitions.
3. Wait for the final observable event-script or alarm marker; tag-write readback alone can precede event completion.
4. Record the end and query only the surrounding Gateway log interval, optionally with a small clock/skew buffer.
5. Inspect the dedicated test logger when one exists and all ERROR-or-higher rows in that interval.
6. Correlate each relevant error to its tag path, alarm, event ID, or logger. Do not dismiss a stack trace because member values are Good.
7. Preserve the time bounds, filters, relevant rows, total/error counts, and an explicit empty result when no errors exist.
8. Apply the same check to failed/stopped attempts and repeats. Good tag values, Good write qualities, clean exports, and expected counters never substitute for the bounded log evidence.

Do not scan or retain the Gateway's entire historical log merely to test one UDT. Query only the interval around creation and testing. If unrelated concurrent errors fall inside the interval, record and classify them separately; do not silently ignore them or attribute them to the UDT. If the bounded log route is unavailable, record the verification gap and do not call the new UDT runtime test complete.

## Root and parameter reads

- A UDT root can return a document snapshot with Good quality, but use direct member reads for authoritative validation.
- Reading a folder value returned `Bad_Unsupported`.
- Both `Parameters.Name` and `Parameters/Name` resolved on the verified build. Prefer the form proved by the target and keep direct reads in regression tests.

## Configuration comparison

The Gateway may omit defaults, reorder members, escape text differently, or normalize line endings. Compare semantics:

- root name, `tagType`, `typeId`;
- parameter name/type/value;
- member name/type/source/data type;
- expression/reference text;
- alarms and event scripts;
- instance overrides;
- complete sibling population in the owning grouped resource.

## Discovery rules

- Enumerate providers; never assume `default`.
- Browse a bounded approved root.
- Require explicit completeness/truncation metadata.
- Browse each concrete `typeId`; a base-only query is not a family query.
- Deduplicate by normalized fully qualified path while retaining source query and concrete type.

## Retry decision

- Safe rejection before writes: correct the request and retry after validation.
- Semantic failure with reliable zero successes: verify no mutation, then retry.
- Partial count, timeout, empty response, connection loss, or missing write qualities: mark unknown mutation and inventory first.
- Accepted configuration with bad runtime quality: do not re-import blindly; inspect configuration, dependent values, and logs.

For a script that calls another Folder's trigger, treat the caller marker as dispatch evidence only. The callee event may run afterward; require its own correlated marker and settled state. A verified prepared-reset run logged caller `COMMITTED` before callee `RESET`, despite a Good trigger write.

For a disarmed timer path, retain the old deadline and wait beyond it before declaring suppression. Require the arm/expression/business state and exact dedicated-log count to remain stable. A clean ERROR query cannot prove that the timer event did not execute.

For renewal, retain every superseded deadline. Wait beyond each one and require the lease still armed, the final deadline unchanged, expiration count zero, and exact log cardinality stable. Then wait beyond the final deadline and require exactly one correlated expiration.

For a renewal cap, exercise the last accepted renewal and the first denied renewal. On denial require the accepted count to remain at the maximum, the general and limit-specific denial counts to advance once, and previous/new/current deadline evidence to equal the last accepted deadline. Continue the same bounded log window through final expiry and both lifecycle resets; inspect exact case logs and all Gateway ERROR-or-higher rows before declaring success.

For an alarm on computed policy state, verify the configured label, ack mode, expressions, associated-data bindings, and complete callback list in the exported UDT. Separately query the exact active source and require priority, UUID, and evaluated context. Confirm a later policy denial keeps the same UUID. At clear, do not require active-time bindings to remain nonzero; correlate `alarmEvent.getId()` against a UUID latched by the active callback, require exactly one active and one clear marker, then prove zero active alarms, Control isolation, cleanup, restoration, and zero ERROR-or-higher rows in the same bounded interval.

For tiered alarms driven by one state transition, check the source set before and after the transition and correlate each tier with its own retained UUID. Require the renewal marker, outgoing-tier clear marker, and incoming-tier active marker exactly once, but compare them as a settled set unless the application explicitly guarantees ordering. Continue through denial, superseded deadline, final expiry, cleanup, and the same-window ERROR-or-higher query to catch duplicate activation or a tier that never clears.

For an alarm on-delay, verify suppression and activation separately. Measure a source-true interval that is strictly shorter than the configured delay, prove the expression was true, then require no active source, callback marker, event UUID, or local latch after it clears and settles. In a fresh cycle, keep the source true until bounded polling finds the exact alarm and active callback; validate its associated data and UUID, clear the source, correlate the clear callback, and require zero residual alarms. Perform the same exact-log and ERROR-or-higher audit for stopped discoveries as for clean repetitions.

For an alarm off-delay at a tier handoff, capture the time immediately before the source-clearing write. Require the outgoing expression false and incoming expression true, then find both active sources before the configured delay. Record distinct UUIDs. Poll until only the incoming source remains, require elapsed time at least the off-delay, correlate the outgoing clear callback, and prove the incoming UUID did not change. Expressions, active alarm sources, and callback latches are separate evidence planes.

For a Manual alarm acknowledged after clear, do not equate no active source with no pending operator work. Require the exact occurrence in `ClearUnacked` state 0, retain its UUID, and prove acknowledgement dry-run does not alter state, evidence tags, callback count, or log cardinality. Apply by exact UUID and require `allAcknowledged`, an empty failure list, `ClearAcked` state 1 with the same UUID, and one exact `alarmAcked` callback. Verify any other alarm tier independently before cleanup.

For an acknowledgement-gated cross-Folder reset, run blank/stale expected-UUID denial, exact-but-unacknowledged denial, and exact-acknowledged acceptance in one bounded interval. Require each denied branch to preserve the coordinator trigger/state. After acceptance, wait separately for the caller's `FORWARDED` evidence and the callee's `RESET` evidence; compare the exact forwarded trigger identity at both planes. Finish with Good QualifiedValues, zero active alarms, Control isolation, cleanup/restoration, exact dedicated-log cardinality, and an all-logger ERROR-or-higher query for the same interval. Audit a stopped structural discovery by the same log rule.

For a consumed-occurrence replay fence, immediately issue a different positive request identity while keeping the same expected and acknowledged UUID. Require `DENIED-REPLAY`, one replay-denial increment, unchanged accepted count, unchanged consumed UUID, zero forwarded value for the denied attempt, and an unchanged downstream reset trigger. Verify exactly one `FORWARDED` and one `DENIED-REPLAY` marker. Reset and read back the consumption latch explicitly during cleanup.

To verify identity-driven re-arming, create and clear a second full alarm occurrence without clearing the first consumed UUID. Require a new event UUID, acknowledge it exactly, and prove it forwards once. Check that previous/current consumption becomes first/second, then replay the second UUID and require both values plus the callee trigger to remain unchanged. Keep both lifecycles, both replay denials, cleanup, and the focused/all-ERROR log queries inside one bounded interval.

For bounded DataSet history, verify configuration and runtime separately. Export must contain the exact columns and types; some Gateway exports encode the DataSet default as a JSON string, so parse it before asserting columns and rows. At runtime, require Good/nontruncated complex reads. After each accepted occurrence verify the exact row lineage and request identity; at the capacity boundary verify oldest-row eviction and the exact counter. After each replay denial compare both serialized rows and QualifiedValue `timestampMillis` with the prior accepted read. Trigger reset through the API, require zero rows and zero evictions, then finish the same-window dedicated and ERROR+ log audit.

Allow the host command timeout to exceed the complete behavioral matrix, while keeping individual status waits below one minute. If the host wrapper ends before the harness `finally` block, classify mutation state as unknown. Use the API to inventory exact tags, complex values, alarms, and the original logger interval; recover through normal reset triggers; query all ERROR-or-higher logs; persist a stopped result; only then retry. A missing result file is not evidence that no mutation occurred.

For runtime parameter changes, verify dry-run through API metadata and unchanged value, not QualifiedValue timestamp. Apply the new value, read it back beside the untouched Control value, exercise behavior that proves the parameter took effect, then restore the original value and verify it again. For compaction, require exact newest-row retention, per-row eviction count, unchanged authorization state, one `COMPACTED` marker, one `NOOP` marker, and unchanged DataSet rows/timestamp on the no-op branch.

For separate accepted and denied histories, prove branch exclusivity in both directions. After every denial, require the exact decision/identity row order and eviction count. Snapshot denial rows and `timestampMillis` before every accepted request and accepted-history maintenance trigger, then require both unchanged afterward. Snapshot accepted history across denial requests in the same way. Exercise enough mixed denials to overflow capacity, reset denial history through its own event trigger, and verify accepted history, consumed UUIDs, accepted/replay counters, and the downstream trigger remain unchanged. Include the reset marker and final zero-row read in the same bounded dedicated and all-ERROR log interval.

For a DataSet plus latest-summary Document, require structural, temporal, and ownership evidence. Export the new Document and its schema parameter from the derived type; inspect inherited DataSet/parameter/script details on the direct parent when the deeper export supplies stubs. At runtime, compare the newest DataSet row's Date milliseconds and all identity fields with the Document after each denial. Compare serialized Document value and `timestampMillis` across every branch that must not write it. After reset, require a complete RESET object rather than absent or stale fields, then prove the accepted-history and authorization planes were untouched.

For a consecutive-denial burst alarm, exercise two complete occurrences. Prove counts below threshold remain inactive, then require the exact active source, a fresh UUID, numeric runtime priority, and associated decision/request/time at threshold. Accept one request to reset the streak, require the alarm to clear with the same UUID, then build a second burst and require a distinct UUID. Because the on-delay callback can race an intermediate log poll, do not demand an exact pre-callback log count after writing the threshold-crossing value; settle on the exact post-callback count instead. Verify active/clear marker pairs by UUID, denial DataSet/Document no-write behavior across acceptance, Control isolation, cleanup/restoration, and the same-window all-logger ERROR+ query.

For a manually acknowledged burst, test both acknowledgment orderings with different occurrences. First clear an unacknowledged burst, prove state 0 and the retained UUID, then acknowledge it into state 1. On the next occurrence, require the active callback to clear all prior acknowledgement evidence, acknowledge while active into state 3, then clear into state 1 while retaining the second UUID, actor, and acknowledgement fields. Require dry-run inertness before both writes, exact `alarmAcked` markers containing UUID/actor/state/cleared context, a quiet Control instance, full evidence cleanup, exact dedicated-log cardinality, and zero all-Gateway ERROR+ entries from before creation through restoration.

For post-burst cooldown, prove both acknowledgement orderings start exactly one cooldown for the matching occurrence. During generation 1, issue a request and require the cooldown-only denial while snapshots and QualifiedValue timestamps for accepted history, denied history, summary, authorization counters, and denial streak remain unchanged. Let generation 1 expire naturally. During generation 2, submit the old generation 1 explicitly and require a `STALE` decision, an incremented stale counter, and `CooldownActive=true`; then require one natural generation-2 expiry. The final interval must contain exactly two `EXPIRED`, one `STALE`, and zero `EARLY` expiry markers, plus Control isolation and restoration.

For a nested cooldown-cancel command, fence the request with both expected generation and source-event UUID. Exercise stale generation, wrong source, accepted cancel, and inactive branches as distinct changing trigger values. Every denied branch must preserve the active cooldown and all accepted/denied history, summary, authorization, alarm, and base cooldown evidence except its own decision counter. On acceptance, disarm `CooldownActive` in a separate first write, then increment the generation and clear deadline/expiry request state before publishing cancellation evidence. Replay the old expiry generation afterward and require inherited expiry handling to report `INACTIVE`, not `EXPIRED` or `EARLY`. Verify exactly one marker for each cancel decision, one isolated Control instance, zero residual alarms, full restoration, exact dedicated-log cardinality, and every Gateway `ERROR+` row from before import through cleanup. A Good cancel-trigger write is not proof that child-to-parent path resolution or the inherited expiry handler worked.

Keep each guarded API read at or below its advertised path maximum. If one logical state assertion grows beyond 64 paths, batch the reads while evaluating the complete expected set on every polling attempt; an oversized single request can return no items and masquerade as a state mismatch. On stopped runs, poll the bounded dedicated and all-logger `ERROR+` queries until the log index is stable, because one immediate query can miss recovery records whose timestamps are already inside the interval.

For a nested cooldown-extension command, fence four denial planes separately: inactive cooldown, stale expected generation, wrong source-event UUID, and an extension outside the positive typed maximum. Each denial may update only its own command evidence and counter; the retained deadline, active generation, expiry request, histories, summary, authorization, alarm evidence, and Control instance must remain unchanged. On acceptance, disarm first, calculate the new deadline from the retained deadline rather than current time, advance the generation, publish DateTime/epoch/expiry-request metadata, and rearm only in a separate final write. Then start another cooldown and prove the inherited cancel command remains independent. Finish with exactly one marker for each extension decision, exact expiry-branch cardinality, zero active alarms, cleanup/restoration, dedicated logs, and all Gateway `ERROR+` rows from before import through restoration.

Reset the occurrence count when `LastCooldownSourceEventId` changes, retain a separate cumulative accepted count, and deny the first request beyond the typed positive maximum as `DENIED-LIMIT`.
