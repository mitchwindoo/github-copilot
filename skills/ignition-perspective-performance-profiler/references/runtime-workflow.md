# Runtime Workflow

## Required Workflow

1. Define the symptom and scenario.
   Record the project, route, target view, user/session class, browser/device class, cache state, what "ready" means, sample interval, repetitions, and success metric. Separate cold load, warm load, navigation, idle dwell, click latency, and multi-session scenarios.

2. Establish Gateway and project context.
   Call `health` first and inspect `runnerVersion`, `stackVersion`, `supportedActions`, `features`, and token state. Treat `supportedActions` as callable actions and `features` as capability flags. Then collect `gatewayInfo`, `projectsList`, `routesList`, `viewsList`, `viewRead`, and `pageValidate` for the target route/view. Save live `viewSha256` values before any write.
   On a new Gateway, after a runner update, or before relying on metric/session/thread evidence, use `scripts/run_gateway_contract_tests.py` to run the read-only G-01 through G-12 contract checks and confirm required actions, feature flags, request envelopes, redaction, bounds, overhead, and no-write proof. When browser/session correlation is included, read the route-to-view mapping from `routesList` or `pageValidate` before passing `--view`; do not use guessed view aliases. Treat `document.title` as shell evidence only: ready text must be visible in the body, or use a stable selector/no-text body readiness check when shell readiness is enough.
   If a profile, incident, recommendation, or acceptance claim depends on a new or changed runner API action, keep a structured runner API workflow report and run `scripts/verify_runner_api_workflow.py <report> --require-shipped` before using that action as evidence. Design-only API gaps may be recorded with `--allow-design-only`, but they must not support proof, recommendations, or release wording until shipped, tested, self-updated on the live runner, versioned, and documented.

3. Run offline static analysis.
   Use `scripts/view_lint.py` or `scripts/profile_view_json.py` against the `viewRead` response or exported `view.json`. Review component counts, embedded/view-canvas/repeater/tab dependencies, binding inventory, tag binding modes, polling candidates, Cache & Share indicators, scripts, table/chart/gauge/media payloads, XY `dataSources`, hidden or persistent content, parameter payloads, and JSON size. Treat results as hypotheses to test.
   When a user has a broad "find the likely heavy routes" request instead of one exact route, use `scripts/rank_routes.py` to rank live routes by static triage signals, then profile a top candidate with runtime evidence before making any claim.

4. Collect synchronized runtime evidence.
   Use `scripts/collect_profile.py` when a read-only evidence bundle is appropriate. It discovers the route/view, runs static analysis, samples `metricsSnapshot`, `gatewayPerformanceSnapshot`, and `perspectiveSessionsQuery`, and writes the manifest/NDJSON/report bundle. Pass `--browser-url` with a stable ready marker or approved selector/text when browser render evidence should be captured in parallel with Gateway sampling. Add focused `logQuery` evidence for WARN/ERROR lines, run IDs, route/view names, and relevant logger suffixes. After the bundle is written, run `scripts/verify_evidence_bundle.py` before using the report as handoff evidence.
   Use `scripts/run_minimal_control_route_profile.py` when R-01 minimal/control route baseline evidence is needed. It wraps cold/warm route-load observations with timeout-aware lifecycle evidence, supports clean-baseline waits before each phase, and writes one composite evidence bundle. Use a stable route URL, explicit browser readiness criteria when available, the configured Perspective timeout plus grace, and `scripts/verify_evidence_bundle.py` before treating it as a control baseline.
   Use `scripts/run_cold_warm_load_profiles.py` when R-02/R-03 cold versus warm route-load evidence is needed. It runs fresh-profile cold observations, one required uncounted shared-profile warm prime, then counted warm observations in that same shared profile. Report cold and warm aggregates separately; do not mix refresh, URL re-entry, back navigation, and fresh browser context in one timing set.
   For click/action latency, pass explicit `--browser-click-*` arguments and require the result marker to be a post-click visible state, not text or UI that was already visible before the click.
   Use `scripts/run_interaction_profiles.py` when the click/action scenario needs repeated observations and a latency distribution.
   Use `scripts/run_navigation_lifecycle.py` when the scenario is repeated control -> target -> control navigation. Prefer `--wait-for-clean-baseline` when retained browser sessions from earlier runs could contaminate pre-samples.
   Use `scripts/run_lifecycle_profile.py` when the question is browser-tab close, session timeout retention, post-close work, or heap/page/session return-to-baseline behavior. When the configured Perspective session timeout is known, pass `--expected-session-timeout-sec`, `--timeout-grace-sec`, and `--require-timeout-coverage`; do not classify retained pages or sessions until the post-close samples cover timeout plus grace.
   Use `scripts/run_idle_dwell_profile.py` when R-07 idle dwell/soak evidence is needed. It holds one browser session open without interaction, samples Gateway/session/metric evidence, requires browser timeline samples when configured, and reports JVM heap slope, Perspective session/page counts, browser heap, DOM, long tasks, and idle counter movement separately. Treat positive slopes or idle counter movement as follow-up flags, not leak proof.
   Use `scripts/run_memory_growth_suspicion.py` on dev/staging or an explicitly approved target when I-04 memory-growth suspicion needs repeated deterministic open/close evidence. It imports one disposable static route/view, repeats fresh browser cycles, baseline-subtracts fixture-new Perspective session/page tokens, samples JVM heap and browser heap separately, then rolls back and verifies cleanup. Compare post-close samples to the configured Perspective timeout; heap movement without retained sessions/pages after the declared timeout is allocation/GC evidence, not leak proof.
   Use `scripts/run_multisession_profile.py` when quantifying 1/5/10 session scaling on staging or another approved target. Prefer `--wait-for-clean-baseline` for sequential groups so retained sessions from prior groups age out before the next group starts. Treat any timed-out or non-zero baseline as contamination unless the scenario intentionally allows existing sessions.

5. Capture incident evidence only when justified.
   During an active freeze, queue backlog, or CPU spike, take one bounded `threadDumpQuery` with narrow filters and the exact confirmation. Label late thread dumps as lower confidence.
   For development-only long-running script or active-freeze capture mechanics, use `scripts/run_long_script_incident.py` on dev/staging or an explicitly approved target. It imports one bounded disposable button-script route, records browser click/result timing, saves an active-window screenshot/timestamp, starts a same-route second browser context during the first session's active window, samples Gateway/session/metric evidence immediately after the click signal, captures one focused bounded thread dump, verifies focused log markers, and rolls back route/view resources. Keep target and max durations small, require visible ready/result markers, and treat the result as fixture mechanics evidence rather than customer freeze proof by itself.
   For development/staging data-source-delay mechanics, use `scripts/run_datasource_delay_incident.py` on an explicitly approved test database. It imports fast and delayed polling-disabled read-only Named Query variants, proves manual `refreshBinding()` changes the query-backed label, compares direct query preview and click-to-result latency, checks browser DOM/long-task/heap and Gateway CPU stability, then rolls back route/view/query resources. Treat the result as I-06 mechanics evidence, not a customer root-cause claim.

6. Classify the bottleneck.
   Use synchronized evidence:
   - Gateway metrics rise while browser stays modest: likely Gateway, binding, script, or data-source cost.
   - Gateway stable while browser long tasks, DOM, heap, or ready time rise: likely browser/component rendering cost.
   - Load time and network bytes rise while CPU remains modest: likely payload, cache, or network cost.
   - Query/fetch duration rises with low Gateway CPU: likely data-source or remote-provider latency.
   - Session queue-length metrics rise during freezes: capture thread evidence and correlate with interaction delay. Treat queue-task counters as supporting activity signals, not as queue-backlog proof by themselves. If executor introspection is available, treat pool/task counters and backing queue class/size as infrastructure context only; a zero executor queue size or zero active count is not proof that no user-visible backlog exists.
   Before any I-02 queue-backlog proof or rejection wording, run `scripts/verify_queue_backlog_claims.py <summary-or-bundle>`. Use `--allow-negative-i02` only when the report explicitly rejects local queue-backlog proof; never use queue-task, script, or property-change counters as a substitute for sustained queue-length rise, recovery, and correlated delay.
   Use `scripts/classify_incident_bundle.py` to post-process an existing live `summary.json` into repeatable triage labels such as browser-rendering pressure, network/payload pressure, database-query activity, or script/queue pressure. Treat labels as hypotheses; missing metric families and single-fixture evidence must stay explicit in the report.

7. Prove or reject remediation.
   A remediation candidate must name the observed evidence, expected primary metric, safety metrics, changed resources, rollback path, and functional equivalence checks. Use dry-run before apply, require current hashes for drift guard, and rerun the same scenario before claiming improvement. Use `scripts/compare_profiles.py` for single bundle comparisons or `scripts/run_paired_profiles.py` for repeated control/target or before/after pairs, but only call the result causal after repeated paired runs meet the declared comparison rule.
   Before accepting recommendations into a handoff report, keep a structured `recommendation-report.json` with `findings[]` and `recommendations[]`. Each recommendation must reference one or more observed finding IDs and declare expected metrics with a direction or threshold. Run `scripts/verify_recommendation_links.py <report-or-bundle> --require-metric-evidence-link` before handoff when the findings carry metric names; treat a failure as a stop condition until the candidate links are repaired.
   Before acceptance wording, keep a structured safety coverage block and run `scripts/verify_safety_coverage.py <summary-or-bundle>`. The V-07 gate must cover CPU, heap, messages or WebSocket activity, duplicate write/message checks, browser/log errors, and operator latency inside declared limits. Treat missing coverage, partial status, duplicate messages/writes, errors, or limit violations as a stop condition.
   Before causal improvement, recommendation, release-ready, or acceptance wording from repeated A/B or remediation evidence, run `scripts/verify_repetition_policy.py <summary-or-report>`. Use `--allow-local-rejection` only when the report explicitly labels local evidence as partial or suggestive and rejects causal/release wording.
   Before turning local/dev fixture evidence into customer-specific recommendation, acceptance, remediation, or release-ready wording, keep a structured `targetEquivalence` block and run `scripts/verify_target_equivalence.py <summary-or-report>`. Include project/route/view aliases, scenario/readiness/browser/cache/session/data-shape matches, and scope-specific query, historian/tag, provider, queue, acceptance, remediation, safety, and rollback proof. Use `--allow-local-rejection` only when the report explicitly labels the evidence as local or partial and rejects customer-specific wording.
   Before calling an acceptance case release-ready, keep a structured `acceptance-case-report.json` and run `scripts/verify_acceptance_case_claims.py <report-or-bundle>`. Use `--allow-local-rejection` only when local/dev mechanics are explicitly labeled partial and the report rejects release wording.

   For a disposable large-table virtualization fixture, use `scripts/run_table_ab_remediation.py`. It creates a guarded before/after package, changes only `props.virtualized`, profiles both variants, compares browser/Gateway evidence, verifies functional equivalence hashes, and rolls back. Use `scripts/run_table_ab_repeated.py` when the table fixture needs repeated observations against the causal comparison rule. Prefer `--wait-for-clean-baseline` when retained sessions from earlier runs could contaminate repetitions, verify the wrapper bundle before report handoff, and inspect `safetyCoverage` before any acceptance wording. Treat a single fixture pass as mechanics proof and suggestive performance evidence until repeated paired runs meet the declared rule; a repeated run that fails the causal policy is a valid rejection of the tested local improvement claim. A partial safety-coverage status means the fixture did not exercise workflow-specific operator latency, duplicate writes/messages, or business correctness.
   For disposable Embedded View breadth scaling, use `scripts/run_embedded_breadth_scaling.py`. It applies 1/10/50/100 child-view instance variants one at a time, validates dependencies, profiles browser/Gateway evidence, compares each count to the baseline, then rolls back and verifies route/view cleanup. Use `--wait-for-clean-baseline` for sequential count comparisons when retained sessions could contaminate deltas. Treat the result as a scaling characterization for the tested fixture, not a universal Embedded View limit.
   For disposable Embedded View nesting-depth scaling, use `scripts/run_embedded_depth_scaling.py`. It applies 1/2/4/6 nested chain variants, waits for a leaf ready marker so the full static chain is proven rendered, compares each depth to the one-level baseline, then rolls back and verifies route/view cleanup. Use `--wait-for-clean-baseline` when retained sessions could contaminate sequential depth deltas. Treat the result as fixture-specific depth evidence, not a platform-wide nesting rule.
   For disposable Embedded View loading-mode checks, use `scripts/run_embedded_loading_mode.py`. It compares `props.loading.order` values with separate parent-first-ready and child-total-ready markers, then rolls back and verifies cleanup. Use `--wait-for-clean-baseline` when retained sessions could contaminate sequential loading-mode deltas. Report first-render and total-ready tradeoffs separately; do not declare a universal `with-parent` or `after-parent` winner from one fixture.
   For disposable hidden-content checks, use `scripts/run_hidden_content_ab.py`. It compares a `meta.visible: false` subtree against a removed-subtree variant, validates readback, profiles browser/Gateway evidence, compares the variants, then rolls back and verifies cleanup. Prefer `--wait-for-clean-baseline` when prior browser sessions could contaminate the variants, and verify the wrapper bundle before report handoff. Report static hidden component/binding deltas separately from runtime/browser evidence; if runtime metrics are mixed, list removal as a candidate to test instead of a proven fix. Require repeated clean-baseline pairs before making a causal recommendation.
   For disposable expression poll-rate scaling, use `scripts/run_poll_rate_scaling.py`. It keeps the same visible component and binding count while changing only expression `now(rate)` values, profiles each rate, compares faster rates against the slowest baseline, then rolls back and verifies cleanup. Use `--wait-for-clean-baseline` for sequential rate comparisons so retained sessions from prior variants do not contaminate per-session deltas. Report freshness requirements beside Gateway/browser cost; do not choose a universal poll rate from one fixture.
   For disposable query polling versus event-driven refresh checks, use `scripts/run_refresh_binding_ab.py`. It compares same-shape query-bound labels with continuous Named Query polling against polling disabled plus a bounded `refreshBinding()` button action, proves the manual click changes a watched query value, then rolls back route/view/query resources and verifies cleanup. Use it when deciding whether query freshness can move from continuous polling to explicit user or workflow events; repeat clean-baseline pairs before causal wording.
   For disposable query Cache & Share checks, use `scripts/run_query_cache_share_ab.py`. It compares same-shape query-bound labels across multiple concurrent browser sessions with Cache & Share off versus on, samples database query timers plus Perspective metrics, verifies exact view readback, and rolls back route/view/query resources. Treat static Cache & Share config as only a hypothesis; only report consolidation when database query counts or equivalent query-activity counters fall by the declared meaningful threshold across repeated clean-baseline pairs. Before recommendation wording, run `scripts/verify_cache_share_claims.py <cache-summary> [sensitivity-summary] --require-sensitive-metric`; use `--allow-rejected-local-claim` only when the wording explicitly rejects a local consolidation claim instead of recommending Cache & Share.
   For disposable tag-history Cache & Share checks, use `scripts/run_tag_history_cache_share_ab.py`. It creates a bounded history-enabled expression-tag fixture under an allowed tag prefix, proves historian rows with `tagRead` and good-sample `historyProbe` evidence on runner `0.3.137+`, compares same-shape tag-history labels across multiple concurrent browser sessions with Cache & Share off versus on, verifies exact view readback and browser-rendered history rows, then rolls back route/view resources. Current runner builds may not expose tag deletion, so use a controlled test prefix and do not claim automatic tag cleanup. Treat static Cache & Share config as only a hypothesis; only report consolidation when database, historian, or equivalent query-activity counters fall by the declared meaningful threshold across repeated clean-baseline pairs. If repeated clean-baseline 1/5/10 session ladders disagree, report threshold instability instead of a stable per-session curve or Cache & Share recommendation. Before tag-history Cache & Share wording, run `scripts/verify_cache_share_claims.py <history-summary> --require-history-evidence`; use `--allow-rejected-local-claim` only when explicitly rejecting the tested local consolidation claim instead of recommending Cache & Share.
   For disposable tag binding mode checks, use `scripts/run_tag_binding_mode_ab.py`. It compares direct local tag bindings, indirect tag bindings through a view parameter, and direct bindings to reference tags backed by source tags; browser-proves initial and updated tag values; profiles concurrent browser sessions; then rolls back route/view resources. Require the profile phase to match the route-specific updated ready text for every browser probe; treat generic Perspective shell loads or missing ready text as failed evidence. Current runner builds may not expose tag deletion, so use a controlled test prefix and do not claim automatic tag cleanup. Treat remote/reference-provider behavior as target-specific; prove provider latency separately from UI binding shape. Before recommendation wording, run `scripts/verify_tag_binding_claims.py <summary-or-bundle> --allow-local-mechanics` for local binding-shape mechanics or `--require-target-provider-evidence` when claiming remote/reference provider behavior. Treat a static `direct` mode on a reference tag as UI binding shape, not provider-latency proof.
   When Cache & Share database-count deltas are flat, noisy, or surprisingly small, use `scripts/run_query_multiplicity_sensitivity.py` before interpreting them. It compares one query-bound property, many properties sharing one query path, and many distinct query paths with Cache & Share disabled, then reports whether the selected database metric is sensitive to the tested same-path or distinct-path query multiplicity. Do not claim Cache & Share success or failure from identical-path deltas when the metric does not visibly respond to the relevant query shape.
   For disposable query parameter-shape checks, use `scripts/run_query_parameter_sensitivity.py`. It compares identical versus distinct Value parameter values on the same Named Query path, with Cache & Share off and on, browser-proves the returned parameter value, samples concurrent sessions, and rolls back route/view/query resources. Treat parameter shape and Cache & Share as separate hypotheses; do not interpret a customer screen's Cache & Share behavior from same-path tests when the real bindings pass distinct parameter values.
   For disposable Tab Container `runWhileHidden` checks, use `scripts/run_tab_runwhilehidden_ab.py`. It activates a work tab, switches back to a control tab, samples Gateway/session/browser evidence during the background hold, compares `runWhileHidden: false` versus `true`, then rolls back and verifies cleanup. Use the default direct-child mode for tabs whose content is embedded directly in the Tab Container, or `--content-mode viewpath` for tabs whose content comes from `props.tabs[].viewPath` child views. For view-path tabs, do not serialize both `text` and `viewPath` on the same tab object; Ignition ignores `viewPath` when `text` is present. Treat `runWhileHidden` as a hypothesis; report browser-retention and Gateway-work effects separately and repeat clean-baseline pairs before recommending a change.
   For disposable Carousel repeated-rotation checks, use `scripts/run_carousel_rotation.py`. It compares `props.lazyLoad: false` versus `true` with the same child views, advances `props.activePane` through a bounded button event, samples browser/Gateway/session evidence during rotation, fails on browser console errors or component-registry render warnings, then rolls back and verifies cleanup. Confirm the target Carousel resource shape from official docs, Designer seeds, or runner seed-read evidence before creating fixtures; do not infer a component type from palette naming alone. Treat `pageValidate` as route/dependency proof, not render proof, and require browser-observed pane and slide-label changes before interpreting lazy-load or retained-view effects.
   For disposable child-view parameter-payload checks, use `scripts/run_parameter_payload_ab.py`. It compares same-visible-shape scalar params against deep object/array params, browser-proves child parameter flow, profiles Gateway/browser/network evidence, then rolls back and verifies cleanup. The default carrier is Embedded View; use `--carrier flex-repeater` for Flex Repeater `props.instances[]` parameters and `--carrier view-canvas` for View Canvas `props.instances[].viewParams`. Treat heavy child-view params as a payload hypothesis; report static parameter bytes, WebSocket/transfer bytes, browser heap, and readiness separately before recommending parameter slimming.
   For disposable table row/column scaling checks, use `scripts/run_table_scaling.py`. It applies a row/column matrix one fixture at a time, profiles static payload, browser timing, DOM, heap, network/WebSocket, and Gateway/session evidence, compares each size to the smallest baseline, then rolls back and verifies cleanup. Treat row count, column count, payload bytes, and DOM/heap as separate hypotheses; do not turn one matrix pass into a universal table limit.
   For disposable Table filter-results writeback checks, use `scripts/run_table_filter_writeback_ab.py`. It compares identical filtered tables with `props.filter.results.enabled` false versus true, profiles property-change, payload, browser, network, WebSocket, and Gateway evidence, compares writeback-on minus writeback-off, then rolls back and verifies cleanup. Treat writeback as a functional-need and cost hypothesis; do not disable it when downstream bindings or scripts require `props.filter.results.data` unless an equivalent design is proven.
   For disposable chart count and point-count scaling checks, use `scripts/run_chart_scaling.py`. It applies documented Time Series Chart fixtures across a chart/series/point matrix, XY Chart fixtures with `--chart-kind xy` across a chart/series/static `dataSources` point matrix, or Gauge fixtures with `--chart-kind gauge` across a gauge/axis/range matrix. It profiles payload bytes, DOM, long tasks, heap, transfer/WebSocket, and Gateway/session evidence, compares each variant to the smallest baseline, then rolls back and verifies cleanup. Treat chart count, series count, point count, XY data-source rows, gauge count, axis count, range count, static payload, and browser work as separate hypotheses; do not infer historian/query/provider cost unless bindings or data-source calls are present and measured.
   For seeded or customer chart shapes where fixture serialization is uncertain, use `scripts/run_seed_view_clone_profile.py`. It reads an existing allowed source view, clones it under a disposable allowlisted view prefix, injects a run-specific ready marker, adds a temporary route, profiles the cloned route with `collect_profile.py`, then rolls back and verifies route/view cleanup. On runner `0.3.98+`, both source-view and disposable target prefixes are exact-or-child boundaries, so do not rely on sibling prefixes. Use it for Power Chart, trend, or Designer-created component shapes before writing a synthetic fixture; do not infer historian, query, provider, or pen cost unless the source view actually exercises those bindings or data sources.
   For disposable property-change storm checks, use `scripts/run_property_change_chain.py`. It applies a bounded button-triggered custom-property write storm, profiles Perspective property-change, script, queue-task, message, browser, network, and Gateway/session evidence, compares larger write counts to the smallest baseline, then rolls back and verifies cleanup. Treat this as controlled storm mechanics for A-18; do not claim a real component `propertyChange` handler loop unless the event shape comes from a proven Designer/runtime resource.
   For disposable transform/script alternative checks, use `scripts/run_transform_cost_ab.py`. It compares same-visible-shape Document/custom-property, expression-only, and property-binding script-transform variants, profiles static script count, Perspective expression/script/property/queue metrics, browser timing, DOM, heap, network/WebSocket evidence, then rolls back and verifies cleanup. Treat script transforms as a cost hypothesis; prove visible output equivalence and runtime impact before recommending a transform move, removal, or rewrite.
