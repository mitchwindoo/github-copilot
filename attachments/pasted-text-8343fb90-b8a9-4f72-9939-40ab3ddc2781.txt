# Production Line — Ignition ↔ PLC Integration Contract (V01)

| | |
|---|---|
| **For** | Ignition / SCADA team, controls (Erick), Operations |
| **PLC program** | `ProductionLine`, 1756-L81E, `MainTask` periodic 5 ms. All tags in this document are **program scope** |
| **Built against** | PLC program export **V05** (2026-09-24). Every tag, UDT field and taught frame in this document was checked against V05 |
| **Status legend** | **LIVE** in V05 · **DERIVE** Ignition computes it from V05 tags · **V02** planned PLC work, not in V05 · **OPS** decision owed by Operations or the team |
| **Date** | 2026-09-24 |

This document is the integration specification. Sections 1–11 are the interface: responsibilities, how to connect, every tag, every handshake and every code. Section 12 answers the SCADA team's review of the PFMEA deck point by point. Section 13 is the roadmap for V02, Section 14 is the acceptance test, and Section 15 lists the open decisions.

---

## 1. Who owns what

| The PLC owns (the authority) | Ignition owns (requests, records, plan) |
|---|---|
| Modes and every mode transition (`modeFSM`) | Requesting modes and commands; showing the result |
| Controlled Stop, IMSTP, interlocks, automatic fault response | Displaying status, faults, why something is blocked |
| Robot motion, stations, CNC handshakes | The **queue plan**: which jobs, which route, which CNC, which cubby |
| Part tracking (`partLocationType/Index`) and job lifecycle | Job identity, SQL records, UniPoint data (frames, maintenance) |
| Resource availability (`processingResources`) | Taking an asset out of service (`maintenanceMode`) |
| Physical stack lights | Mirroring the lights on screen; login, roles, audit trail |

**Safety never passes through Ignition.** Ignition has no IMSTP and no E-stop command. The E-stops, light curtains and door interlocks act in the PLC. A checklist that an operator ticks in Ignition is a **record**. Where the PFMEA makes an Ignition action a permissive (the SCADA resume command, slide 10), the PLC enforces it (§13, V02-2).

**The PLC is the authority on in-flight jobs.** SQL and UniPoint mirror the PLC's job status (§7.4). They never override it.

## 2. Connecting

| Item | Value |
|---|---|
| Driver | Ignition **Allen-Bradley Logix** driver (EtherNet/IP) to the L81E |
| Tag path | `Program:ProductionLine.<tag>` e.g. `Program:ProductionLine.modeFSM`, `Program:ProductionLine.stagingQueue[3].operations[0].userFrameNumber` |
| Types | BOOL, DINT (Int4), REAL (Float4), LINT (Int8: µs since 1970-01-01 UTC), STRING (Logix STRING, 82 chars max) |
| Suggested Ignition UDTs | Mirror `productionQueueEntryUdt`, `jobOperationUdt` and `resourceStatusUdt` field for field (§6.2) |
| Scan rates | Handshake and mode tags: **100 ms**. Status and resources: 250–500 ms. Queue arrays: leased or on demand, only for the slots on screen |
| Write security | Ignition may write **only** the tags in §3.1. Make every other tag read-only in the Ignition tag provider. The PLC doesn't lock them |
| Test Clear | `testClearRequest` wipes the production queue. Restrict it to one commissioning role and keep it off production screens |

**Writes aren't atomic.** A multi-tag write reaches the PLC as several CIP packets, and the PLC scans every 5 ms, so it can see half of a write. Every handshake below therefore runs as: write the data → read it back → raise the request in a **separate** write. Mitchell's FAT (2026-09-16) caught the PLC acting on a request before its data had arrived.

## 4. Modes

### 4.1 How each request behaves — LIVE

| Request | Ignition must |
|---|---|
| `autoModeRequest` | Hold it high for as long as Auto is wanted; dropping it leaves Auto. **The PLC clears it on any fault**, so after a reset the operator requests Auto again |
| `stopModeRequest` | Raise it, wait for `modeFSM` = 0, then drop it. The PLC never clears it, and while it's held every Auto request is cancelled |
| `manualRecoveryModeRequest`, `engineeringModeRequest`, `maintenanceModeRequest` | Hold for as long as the mode is wanted. Drop one before requesting the next |
| `cellPauseRequest` | Set once; the PLC clears it when Paused is reached |
| `cellResumeRequest` | Set once; the PLC clears it when Auto is reached. It needs `resumePermissivesOk` and `autoModeRequest` still high. **It stays latched until then**, so the line resumes by itself once the doors close. Clear it from Ignition if the operator gives up (§15-1) |
| `testClearRequest` | Hold ≥ 5 s. Afterwards send a full queue sync, because the production queue is empty |

**Every mode change goes through Stopped (0).** A fault forces Stopped from any mode, because the PLC clears every mode request while `systemFaulted`. No mode can be entered until the fault is reset.

### 4.2 Transitions and what the operator sees

| From → To | PLC condition | Operator sees during the transition (DERIVE) |
|---|---|---|
| Stopped → Auto | `autoModeRequest`, not faulted | — |
| Auto → Stopped (Controlled Stop) | `stopModeRequest`, a fault, or the Auto request dropped | `modeFSM` = 0 at once, but **"Stopping — Rikku finishing its move"** while `rikkuOperationActive` = 1. Stopped and parked when `rikkuFSM` = 10 and `rikkuWithinHomeMargin` = 1 |
| Auto → Paused | `cellPauseRequest`, Rikku not reserved, no door open | **"Pausing"** while `cellPausePending` = 1 (flashing amber on the HMI). Paused when `cellPaused` = 1 |
| Paused → Auto | `cellResumeRequest`, `resumePermissivesOk`, Auto still requested | "Resume blocked: door open / light curtain" from `anyDoorOpen` and `lightCurtainBroken` |
| Stopped → Manual Recovery / Maintenance / Engineering | Request held, not faulted | — |
| Any → Stopped on IMSTP | Critical fault (E-stop, light curtain, unclamp failures) | `faultIsCritical` = 1; Rikku stops where it stands (`rikkuFSM` = 0). The interrupted job is **held with error 80** |

### 4.3 Rejection reasons — DERIVE now, V02 from the PLC

The PLC doesn't answer a refused mode request; it just stays where it is. Until the PLC reports a reason (§13, V02-1), show the first matching line:

| Request | Blocked because (first true) |
|---|---|
| Any mode | `systemFaulted` → "Reset faults first (`faultResetCount`/`faultResetCountRequired`)" · `stopModeRequest` still high → "Release Stop" · `modeFSM` ≠ 0 and the target isn't reachable directly → "Go to Stopped first" |
| Auto from Paused | `NOT resumePermissivesOk` → "Close doors / clear light curtain" · `NOT autoModeRequest` → "Auto not requested" |
| Pause | `cellPausePending` = 1 → "Pausing: waiting for Rikku to finish and doors to close" |
| Queue update | `NOT scadaAcceptAuthorityGranted` → "Queue changes only in Auto" |

### 4.4 Auto readiness checklist (slide 10)

| Checklist item | Ignition shows (DERIVE) | PLC enforces today |
|---|---|---|
| Doors closed | `NOT anyDoorOpen` | For Resume only |
| Light curtain clear | `NOT lightCurtainBroken` | For Resume only |
| E-stops reset | `NOT lineEStopActive`, `NOT anyCellEStopActive` | Line E-stop via the fault |
| Alarms/faults reset | `NOT systemFaulted` | Yes |
| Robot at a known location | `rikkuWithinHomeMargin` | No |
| SCADA resume / job validation | Ignition's own checks | No |

The full checklist as a PLC permissive for Auto is V02-2.

## 5. Faults and reset

### 5.1 Reset — LIVE

- Pulse `systemReset` once per press. The PLC counts rising edges. **Critical faults need 2 presses, non-critical 1** (`faultResetCountRequired`). Release between presses. The reset completes on release (`faultResetComplete`).
- A critical fault whose cause is still present re-trips. For example, a line E-stop still pressed keeps `systemFaulted` = 1.
- HMI reset and physical reset are the same thing to the PLC: one tag, `systemReset`. Slide 10 allows either.

### 5.2 Fault catalogue — LIVE (V05)

| Indicator | Log text | Class | Presses | Enabled | Debounce |
|---|---|---|---|---|---|
| `fault1TimeoutFlag` | `FAULT-01: RIKKU UNCLAMPING FAILED` | Critical (IMSTP) | 2 | All modes except Engineering | 10 s |
| `fault2TimeoutFlag` | `FAULT-02: E-STOP PRESSED` | Critical | 2 | Always | 10 ms |
| `fault3TimeoutFlag` | `FAULT-03: LIGHT CURTAIN BROKEN` | Critical | 2 | Not in Engineering, Maintenance or Paused (curtains disabled there) | 10 ms |
| `fault4TimeoutFlag` | `FAULT-04: ASSET UNCLAMPING FAILED` | Critical | 2 | All modes except Engineering | 10 s |
| `fault5TimeoutFlag` | `FAULT-05: RIKKU FAULTED` | Fault | 1 | Not in Engineering, and not while Rikku is in IMSTP or fault reset | 10 ms |

- **What the flag means:** `faultNTimeoutFlag` is high while that fault's cause is present (after the debounce) and drops when the cause clears. The line stays faulted (`systemFaulted`) until it is reset, even after every flag has dropped.
- **Alarm summary:** raise an alarm on each flag's rising edge (or on a new log entry, below), keep it until the reset completes (`faultResetComplete`), and show "cause still present" while the flag is high. Ignition timestamps it and records acknowledgement and the user.
- **History:** when `faultBufferIndex` changes, read `faultMessageBuffer[faultBufferIndex − 1]` (it's a ring of 250) and store it with Ignition's timestamp. The PLC buffer has no timestamps. `faultHistoryReset` clears only the PLC ring.
- **Alarms (`systemAlarmed`) aren't used yet.** Alarm escalation and the 65 fault-matrix rows still to build come with the fault expansion (V02-3). Escalations that act on equipment, such as single-blocking the CNCs on waste water, chip bin or hopper, will live in the PLC. Ignition shows them and sends the emails.

## 6. The queue plan

### 6.1 Principle

Ignition owns the plan and publishes it whole. The PLC accepts the plan only in Auto, validates every entry, then copies it into `productionQueue`. A publish **may replace future work and never interrupts work already started.** Changes such as inserting, re-ordering or re-assigning a CNC all go through the same step: edit the plan, then publish it again.

### 6.2 A staging entry

Header, `stagingQueue[i]`:

| Field | Type | Rule (checked by the PLC, error 20 unless noted) |
|---|---|---|
| `valid` | BOOL | 1 for every slot `0 .. stagingQueueCount−1`, with no gaps |
| `jobId` | DINT | > 0; **unique** in the plan (duplicate → error 30). The PLC tracks reservations by it |
| `jobNumber`, `partNumber`, `serialNumber` | STRING | Traceability; returned in the result |
| `loadCubbyIndex` | DINT | 1–5. **The part is already in this cubby** when the job is published |
| `unloadCubbyIndex` | DINT | 1–5. Must be empty (the PLC has no part-present check on it) |
| `operationCount` | DINT | 2–50 |
| `assignedCncAssetId` | DINT | Vertical CNC for the **whole job**: CATA_01–04 = asset 2–5; 0 if the route has none |
| `fixtureType`, `assignedCncType` | DINT | Carried, not used by the PLC |

Leave the lifecycle fields alone (`status`, `errorCode`, `currentOperation`, `requestedResourceType`, `activeResourceIndex`, `nextResource*`). The PLC doesn't copy them.

Operation, `stagingQueue[i].operations[n]`, n = 0 .. `operationCount−1`:

| Field | Type | Rule |
|---|---|---|
| `valid` | BOOL | 1 |
| `operationCode` | DINT | op 0 = **10 MKIT**, last = **130 UNLOAD**, every op in between 20–120 (§11.1) |
| `assignedCncAssetId` | DINT | Horizontal CNC ops only: CATH_01 = asset 6; 0 otherwise |
| `programNumber` | DINT | CNC ops: the work number the CNC must report before cycle start |
| `fixtureOrientation` | DINT | Carried |
| `userFrameNumber` | DINT | Expected frame for this op (§6.6) |
| `userFrameValid` | BOOL | 1 once the coordinates are written |
| `userFrameXcoords` … `userFrameRcoords` | REAL ×6 | From UniPoint, for this part's fixture: mm and degrees. **This is where Rikku goes** (§6.6) |

Operations beyond `operationCount` are ignored. Ignition need not write them.

### 6.3 Publish handshake — LIVE

```
Ignition                                     PLC (_04)
1  write stagingQueue[0..count-1], stagingQueueCount
2  read back, compare
3  queueUpdateRequest := 1  ──────────────▶  only in Auto (scadaAcceptAuthorityGranted)
                                             10 validate each slot        1 slot / 5 ms
                                             12 check slots above count
                                             20 copy each slot            1 slot / 5 ms
                             ◀──────────────  queueUpdateAck := 1          (accepted)
   or                        ◀──────────────  queueSyncFSM = 90, queueSyncErrorCode ≠ 0 (rejected, nothing changed)
4  queueUpdateRequest := 0  ──────────────▶  Ack := 0, error cleared, back to idle
```

- Don't touch staging from step 3 until the Ack or reject. Allow **5 s**; 256 slots take about 2.6 s.
- A request raised outside Auto gets no answer; it runs when Auto is entered.

| `queueSyncErrorCode` | Meaning | What the operator does |
|---|---|---|
| 10 | Count ≤ 0 or > 256, or a smaller count would drop a job that has started or hasn't reported | Keep the count until those jobs finish and report |
| 20 | An entry fails §6.2 | Fix the entry named in Ignition's own pre-check |
| 30 | Two entries share a `jobId` | Fix the plan |

**Validate in Ignition first**, with the same rules, and name the slot and field. The PLC's code only says which rule failed, not which slot.

### 6.4 What a publish does to jobs already running — LIVE

A job has **started** once it is In Process (50), or once it is Held, Waiting or Ready (20/30/40) and any of these is true: `currentOperation` > 0, its part has left the load cubby, or its next resource is already secured.

| Slot at publish time | Result |
|---|---|
| Empty, not started, or finished and reported | Replaced by the new entry |
| Started, **same `jobId`** | Data refreshed (frames, program numbers, later ops); status and progress kept |
| Started with a **different** `jobId`, or In Process | **Deferred:** `productionQueuePendingSync[i]` = 1; the running job is untouched |
| Finished but result not reported | Deferred |

- **A deferred entry isn't applied by itself.** Once that slot's result has been reported, publish again. The flag clears when the slot is copied.
- **Slots are stable.** A job keeps its slot from publish until its result is reported. Never move a job to another slot, because the PLC would treat it as a new job.
- **Removing a job that hasn't started:** publish without it. Either shrink the count, if it was the last slot, or put another job in its slot.
- **Changing a started job's CNC isn't possible.** A vertical CNC is held for the whole job once the job reaches it.

### 6.5 Planning rules Ignition must follow

- The **load cubby stays dedicated** to its job until the job's result is reported. It's the park buffer: after 30 s without a next station, Rikku parks the part back in its own load cubby. Don't stage a new part in it early.
- Only publish a job whose part the operator has confirmed in the load cubby.
- Keep **one unload cubby per job** until the operator empties it.

### 6.6 User frames: how to populate them in every job

**What the numbers do.** For each robot move, the PLC hands Rikku the operation's X Y Z W P R, and Rikku writes it into **PR[1:plcDynamicUF]**. The TP program sets `UFRAME[1:dynamicFrame] = PR[1]` and runs its taught pick/place points **relative to that frame**. **The coordinates Ignition writes are the frame Rikku moves in.** The frame **number** is a label that the PLC checks. The PLC then takes the rail position and the side (left/right) from its own taught table `rikkuUserFrameDatabase[number]`.

**What X Y Z W P R are.** They define the user frame of **this part's fixture at this asset and side**: origin X Y Z in **mm** and orientation W P R in **degrees**. They use the same reference and conventions as the taught frames in `rikkuUserFrameDatabase[n].xCoords … rCoords`, which Ignition can read. For the nominal fixture, the job's values equal the taught frame. UniPoint supplies the per-fixture values.

**What the PLC checks, and what it doesn't.**

| Check | Who | Failure |
|---|---|---|
| `userFrameNumber` = the expected frame for this asset and side (table below) | PLC | Held 20 / error 50, before any pick |
| `userFrameValid` = 1 | PLC | Held 20 / 50 |
| The asset frame is taught (`rikkuUserFrameDatabase[n].valid`) | PLC | Held 20 / 50 |
| **X Y Z W P R are plausible** | **Ignition, before publishing** | **The PLC does not check coordinates.** A wrong value sends Rikku to a wrong place |

**Ignition must check every operation's coordinates against the taught frame** `rikkuUserFrameDatabase[userFrameNumber]` and refuse to publish if any axis differs by more than the agreed tolerance (§15-7). Also refuse a zero or missing coordinate set.

**Which frame number, per operation:**

| Operation | `userFrameNumber` | X Y Z W P R from UniPoint for… |
|---|---|---|
| 10 MKIT (op 0) | 100 + `loadCubbyIndex` | the part's fixture in its **load cubby**. Also used to **park** the part back in that cubby |
| 20, 30 (CATA A-side) | 200 + CATA number, where CATA number = `assignedCncAssetId` − 1 (asset 2 → CATA_01 → 201) | the fixture on that CATA, A-side |
| 40, 50 (CATA Opp-A) | 250 + CATA number | the fixture on that CATA, Opp-A |
| 60 / 70 (CATH) | 301 / 351 | the fixture on CATH_01, A / Opp-A |
| 80, 90 (wash) | 451 | the fixture in Washer_01 |
| 100 (flow) | 651 | the fixture in Flow_01 (disabled) |
| 110 / 120 (RSP) | 501 / 551 | the fixture in RSP_01, A / Opp-A |
| 130 UNLOAD (last op) | 150 + `unloadCubbyIndex` | the part's fixture in its **unload cubby**. Frames 151–155 are copies of 101–105 until Erick teaches them |

**Worked example.** Route MKIT → CATA A-side → CATA Opp-A → quick wash → UNLOAD. Load cubby 2, unload cubby 2, CATA_02 (`assignedCncAssetId` = 3), nominal fixture. The values are V05's taught frames:

| op | `operationCode` | `userFrameNumber` | X | Y | Z | W | P | R |
|---|---|---|---|---|---|---|---|---|
| 0 | 10 | 102 | 812.284 | 700.000 | 389.781 | 0.270 | −6.862 | 1.819 |
| 1 | 20 | 202 | 811.642 | −700.000 | 291.482 | 0.668 | −6.874 | 177.665 |
| 2 | 40 | 252 | 811.642 | −700.000 | 191.482 | 0.668 | −6.874 | 177.665 |
| 3 | 80 | 451 | 812.642 | −700.000 | 186.482 | 0.668 | −6.874 | 177.665 |
| 4 | 130 | 152 | 812.284 | 700.000 | 389.781 | 0.270 | −6.862 | 1.819 |

`userFrameValid` = 1 on every row, `operationCount` = 5. For a different fixture, UniPoint's values replace these, within tolerance of the taught frame.

**Rules:**
- Write the frames **before** publishing (§6.3). A job with a missing frame is held at the first move that needs it.
- **Correcting a frame** on a job that has started: re-publish the slot with the **same `jobId`** and the new values, then Rewind in Manual Recovery if the job is already held with error 50 (§9).
- If Erick re-teaches an asset frame, `rikkuUserFrameDatabase` changes. Ignition re-reads it for its tolerance check, and UniPoint's values must be updated to match.
- **Limit:** for washer and RSP the PLC chooses the unit. With one unit of each the frame is predictable; a second unit needs a decision (§15-2).

## 7. Jobs

### 7.1 Status (`productionQueue[i].status`)

| Code | Status | Meaning |
|---|---|---|
| 0 | Empty | No job |
| 10 | Queued | Accepted, not yet evaluated |
| 20 | **Held** | Stopped by a PLC check; see `errorCode`. **Needs Manual Recovery** |
| 30 | Waiting for resource | Its next resource is busy; `errorCode` says which kind |
| 40 | Ready for dispatch | Its next operation is ready to be dispatched |
| 50 | In process | A resource is working on it |
| 100 | Complete | Finished, part in the unload cubby |
| 110 | Aborted | Scrapped through Manual Recovery |

### 7.2 Error codes (`productionQueue[i].errorCode`, also `resultCode`)

| Code | Meaning | Operator action |
|---|---|---|
| 0 | None | — |
| 10 | Invalid entry | Fix the plan |
| 20 | Resource blocked (washer/RSP/flow/robot busy); with status 30 it just means waiting | None, or check the asset |
| 30 | Cubby blocked | Clear the cubby |
| 40 | Assigned CNC unavailable or invalid (with status 30: CNC busy; with status 20: invalid assignment) | Wait, or re-plan the job to another CNC if it hasn't started |
| 50 | Frame number doesn't match the asset/side, or the asset frame isn't taught | Correct the frame (§6.4, same `jobId`), then Rewind |
| 60 | Rikku rejected the command frame | Check the frame data |
| 70 | Door didn't open or close within 10 s | Check the door, then Rewind |
| 75 | Door didn't read closed before opening | Check the sensor |
| 80 | Rikku's move was interrupted (IMSTP, robot fault or comm loss) | Manual Recovery: Rewind, Override or Scrap |
| 90 | Station didn't report ready within 15 s | Check the station |
| 95 | Station faulted while processing | Check the station, then decide |

### 7.3 Part location (`partLocationType[i]` / `partLocationIndex[i]`)

| Type | Where | Index |
|---|---|---|
| 0 | On Rikku | — |
| 1 / 2 | Vertical / horizontal CNC | resource index |
| 3 / 4 / 5 | Washer / RSP / Flow | resource index |
| 10 | Load cubby | cubby 1–5 |
| 11 | Unload cubby | cubby 1–5 |
| 12 | None | — |
| 13 | Scrap | — |

Operation progress: `operations[n].operationStatus` = 0 not started · 10 ready · 20 in process · 100 complete. The times are `operationStartTime` / `operationEndTime` (LINT, µs UTC).

### 7.4 Keeping SQL and UniPoint consistent with the PLC

| PFMEA / SQL action | PLC mechanism | PLC status afterwards |
|---|---|---|
| **Repeat** an operation | Manual Recovery **Rewind** to that op | 40, then continues |
| **Abort** a job | Manual Recovery **Scrap** | 110; result reported with `resultStatus` 110 |
| **Correct location** | Manual Recovery **Override** | 20 (held) until Rewind or Scrap |
| **Skip forward** ("skip wash", slide 13) | Not available | **V02-6** |
| Complete | Normal flow | 100; result reported |

SQL takes a job's final state **only from the result mailbox**, and in-flight state from `productionQueue[i].status`. Ignition never writes a status.

### 7.5 Result mailbox — LIVE

```
PLC (_10)                                         Ignition
loads resultJobId, resultJobNumber,
resultResourceAssetId, resultCode, resultStatus
resultReportPending := 1  ───────────────────▶   read all five fields, write to SQL
                          ◀───────────────────   resultReportAck := 1
resultReportPending := 0  ───────────────────▶   resultReportAck := 0
(the next result loads only once the Ack is low)
```

- `resultStatus` = 100 Complete or 110 Aborted. Use it, not `resultCode`: a scrapped job can carry code 0.
- `resultResourceAssetId` = the asset the job was last on.
- One result at a time. Results aren't reported in Engineering; they queue and flow afterwards.
- Test Clear empties the mailbox, and an unacknowledged result is lost. Reconcile SQL after a Test Clear.

## 9. Manual Recovery console

These commands are accepted **only in Manual Recovery (20)** and only while Rikku is idle (`rikkuOperationActive` = 0). Each is four-phase: write the fields → raise `…Request` → wait for `…Accepted` = 1 (applied) or `…ErrorCode` = 10 (invalid job, index out of range, or wrong state) → drop the request. Don't change the fields while the request is up.

| Command | Fields | Accepted when status is | Effect |
|---|---|---|---|
| **Rewind** (repeat) | `JobIndex` = slot 0–255, `ToOperation` = 0 … `currentOperation` | 50, 20, 100 | Undo progress back to that op, release what the job holds, reset the station sequence, hand it back to dispatch |
| **Scrap** (abort) | `JobIndex` | Anything but 0 and 110 | Release everything; status 110, location 13; result reported |
| **Override** (location) | `JobIndex`, `LocationType`, `LocationIndex` (§7.3) | 50, 20 | Records where the part really is; job held (20) |

- **After an IMSTP** (error 80), Rikku never restarts a half-done program by itself. The operator looks at the cell, uses `rikkuWithinHomeMargin` (slide 11's "near home" flag), and chooses Rewind (repeat the move), Override then Rewind (the part is elsewhere), or Scrap.
- To fix a held job's data (e.g. error 50): re-publish the slot with the **same `jobId`** in Auto, then Stop → Manual Recovery → Rewind → Stop → Auto.
- Robot moves in Manual Recovery are the dispatched job's own moves. Jogging Rikku from the HMI step by step (slide 13) is V02-6.
