<technical_details>
- **Root cause of the reported bug**: `NewBranchWindow.xaml` had a hard-coded `Height="240"` with `ResizeMode="NoResize"`. The actual required content height (header + 2 labeled TextBoxes + spacer + footer buttons) exceeded 240px on this machine's font/DPI rendering, silently clipping the Start Point field and the Cancel/Create buttons at the bottom edge — a real, user-visible, accessibility-relevant defect that pure UIA-automation-based testing (checking element existence/state/text) never caught, since FlaUI could still find and invoke the clipped controls via the accessibility tree even though a human couldn't see or easily click them.
- **Fix**: Replaced fixed `Height="240"` with `SizeToContent="Height"` (kept `Width="480"`, kept `ResizeMode="NoResize"`). This makes WPF auto-size the window's height to its actual rendered content regardless of font metrics/DPI, eliminating this entire class of bug. Confirmed via screenshot: window auto-grew to 296px and all content + buttons became fully visible.
- **FlaUI screenshot capture quirks discovered** (important for future work in this environment):
  - `FlaUI.Core.Capturing.Capture.Element(AutomationElement, CaptureSettings?)` and `Capture.Rectangle(Rectangle, CaptureSettings?)` (even using a freshly-read `window.BoundingRectangle` immediately before the call) both produced **mismatched/stale crops** on this dev machine — capturing pixel content that visually matched a different window/region than the target element's reported bounding rectangle. This happened consistently across multiple attempts, including with added settle-delays (`Thread.Sleep`) and post-render-readiness checks (waiting for a child control to exist). Root cause suspected to be DPI-scaling/remote-desktop-scaling mismatch between UIA logical coordinates and physical screen-capture coordinates in this specific environment — not an application bug.
  - **Workaround**: `Capture.MainScreen()` (full desktop screenshot, no per-element cropping) reliably and correctly captured the real, current on-screen state every time. This is the pattern to use for future screenshot-based UI validation in this environment, accepting the tradeoff that captured images include the whole desktop (other windows, IDE, etc. may be visible) rather than a clean crop of just the target dialog.
  - `Capture.MainScreen()`, `Capture.Screen(int, CaptureSettings?)`, `Capture.ScreensWithElement(...)` are the other static capture entry points available in FlaUI 5.0.0, if further experimentation is wanted.
- **Testing philosophy takeaway (explicitly stated by user)**: automated UIA-based assertions (element exists, is enabled, has expected text/name) are necessary but **not sufficient** to prove a feature "works" — visual/rendering defects (clipped controls, overlapping content, unreadable text) can pass every UIA assertion while being completely broken for a real user. Going forward, the testing loop for any UI work should include actual screenshot capture and visual review, not just property-based assertions.
- Unresolved/open question: should the screenshot-capture step become a permanent, automated part of `GitHistoryUiTests.cs` (producing artifacts on every run, e.g. to a `%TEMP%` or `TestResults`-style folder), or should it remain an ad hoc diagnostic technique I use before declaring UI work complete? The user's phrasing ("in your testing loop, screenshot each interaction") suggests they want this to be a standing practice, likely baked into the persisted test rather than only used reactively — leaning toward integrating it permanently.
- Other pre-existing windows (`CloneRepositoryWindow.xaml` `Width=560 Height=230`, `GitRepositoryActionWindow.xaml` `Width=420 Height=200`) use the same fixed-height anti-pattern and are unverified — flagged as a risk but out of scope for this fix (not part of the Git History feature being tested), per repo convention of not fixing unrelated pre-existing issues without being asked.
</technical_details>
